# make_notion

현재 git 브랜치에서 한 작업을 **비즈니스 담당자가 읽고 이해할 수 있는 설계 공유 문서**로 정리해, 노션 **인덱스 페이지**의 하위 페이지로 남기는 스킬.

**인덱스 페이지**는 작업별 하위 페이지가 쌓이는 노션 페이지다(예: "<이름> Task 현황"). 사용자가 이름이나 URL 을 주면 그것을 쓴다. 주지 않았으면 사용자의 CLAUDE.md·메모리에 적힌 페이지를 쓰고, 거기에도 없으면 한 번 묻는다. 이 문서에서는 그 페이지를 「인덱스 페이지」라고 부른다.

## 목적과 배경

브랜치 작업이 끝나거나 중간 공유가 필요할 때, "이 결과물이 무엇이고 어떻게 동작하는지"를 손으로 정리해 노션에 옮기는 일은 반복적이고 빠뜨리기 쉽다. 이 스킬은 git 이 들고 있는 사실(커밋 메시지, 변경 파일, diff)과 실제 소스·스펙을 수집한 뒤, 그것을 설계 공유 문서로 바꿔 노션에 남긴다.

산출물이 지키는 기준은 세 가지다.

1. **독자는 비즈니스 담당자다.** 본문은 코드 이름 없이 일상어로 쓴다. 개발자에게 필요한 상세는 접힌 「개발자 참고」 토글 한 곳에 모은다. 사용자가 "개발자용"이라고 말했을 때만 본문 수준을 올린다.
2. **그림은 전부 diagram-design PNG 다.** 구조도·흐름도·시퀀스·분기도를 가리지 않는다. mermaid 코드블록은 쓰지 않는다. 노션의 mermaid 렌더는 작고 라벨이 겹쳐서 읽기 어렵다.
3. **사실만 적는다.** 커밋·diff·소스에 없는 내용을 지어내지 않는다. 노션 기록은 나중에 근거 자료로 쓰이므로 정확성이 곧 가치다.

산출물은 "무슨 커밋을 했다"는 작업 로그나 단계별 구현 계획이 아니다. 완성된(또는 설계가 확정된) 결과물의 구조·동작·설계 의도를 독자가 이해하도록 쓰는 문서다.

## 플러그인 사전 고지

이 스킬은 플러그인 세 개와 CLI 하나에 기댄다. 시작할 때 설치 여부를 확인해 채팅 첫 줄에 한 번 알린다. 필수 플러그인이 없으면 그 자리에서 멈추고 설치 명령을 안내한다.

| 플러그인 | 필수 | 쓰는 곳 | 없을 때 | 설치 |
|---|---|---|---|---|
| Notion (`notion@claude-plugins-official`) | 필수 | 3~6단계 페이지 조회·미리보기·하위 페이지 생성·갱신(`mcp__plugin_Notion_notion__*` 도구) | 멈춘다. 문서는 로컬 Markdown 으로만 남긴다 | `/plugin install notion@claude-plugins-official` 뒤 Notion 로그인 |
| diagram-design (`diagram-design@diagram-design`) | 필수 | 2단계 모든 그림(구성도·흐름도·시퀀스·분기도·모듈 관계도) PNG, `self_check.py`, `import-mermaid` | 멈춘다. mermaid 나 다른 도구로 대신 그리지 않는다 | `/plugin marketplace add cathrynlavery/diagram-design` → `/plugin install diagram-design@diagram-design`. 브랜드 프로필은 `~/.diagram-design/profiles/<이름>.md`(없으면 기본 토큰을 쓴다) |
| ego-browser (ego lite 앱의 CLI) | 필수 | 2단계 PNG 추출(`scripts/export_png.sh`) | 멈춘다. HTML 원본까지만 만들고, 다른 브라우저 도구로 대신 찍지 않는다 | [citrolabs/ego-lite](https://github.com/citrolabs/ego-lite) 의 안내대로 ego lite 를 설치한다 |
| pstack (`pstack@cursor-plugins`) | 기본 사용 | 1단계 `teach`·`how`·`why` 로 조사하고, 2단계에서 `teach` 의 설명 방식으로 쓴다 | 채팅 첫 줄에 pstack 없이 쓴다고 알리고, 1단계 수집과 직접 읽은 소스만으로 쓴다 | `/plugin marketplace add cursor/plugins` → `/plugin install pstack@cursor-plugins` → `/pstack:setup-pstack` |

확인 한 줄:

```bash
ls "$HOME"/.claude/plugins/cache/diagram-design/diagram-design/*/skills/diagram-design/SKILL.md "$HOME"/.claude/plugins/cache/cursor-plugins/pstack/*/skills/teach/SKILL.md 2>/dev/null
```

Notion 은 도구 목록에 `mcp__plugin_Notion_notion__notion-fetch` 가 있는지로 본다. PNG 추출에는 ego-browser(`command -v ego-browser`)가 필요하다. Playwright MCP 와 claude-in-chrome 은 쓰지 않는다.

## 워크플로우

### 1단계: 작업 내용 수집 (결정적)

번들 스크립트로 브랜치 작업을 모은다. 매번 git 명령을 새로 짜지 말고 이 스크립트를 쓴다(일관성·속도):

```bash
bash "<이 스킬의 base 디렉터리>/scripts/gather_branch_work.sh"
```

(base 디렉터리는 스킬을 실행할 때 알려 주는 경로다.)

- 베이스 브랜치는 기본 `develop` 이며, `origin/develop` → `develop` → `origin/main` → `main` 순으로 자동 탐색한다. 원격 추적 브랜치를 먼저 고르는 이유는, 로컬 베이스가 뒤처져 있으면 다른 사람의 커밋이 이 브랜치 작업으로 섞이기 때문이다.
- 사용자가 다른 베이스를 지정하면 인자로 넘긴다: `... gather_branch_work.sh main`
- 출력 섹션: `BRANCH`, `BASE`, `COMMITS`, `DIFFSTAT`, `FILES CHANGED`, `UNCOMMITTED`.
- 출력 첫 줄이 `WARNING` 이면 현재 브랜치에 베이스 대비 커밋이 없다는 뜻이다(베이스 브랜치 위에 있거나 이미 머지된 경우). 빈 결과로 문서를 쓰지 않는다. 사용자에게 PR 번호를 받아 `gh pr view <N> --json commits,files,body` 로 같은 사실을 모은다.

커밋 메시지만으로 의도가 불분명한 변경이 있으면, 해당 파일의 diff 를 직접 확인해 보강한다(`git diff <base>...HEAD -- <path>`). 추측은 하지 않는다. 모르면 적지 않는다.

**pstack `teach`·`how`·`why` 로 조사한다(기본 절차)**: 수집이 끝나면 2단계 전에 `teach` 스킬을 돌린다. `teach` 는 `how`(어떻게 동작하나)와 `why`(왜 이렇게 만들었나)를 실행하고, 두 결과를 한 편의 평이한 설명으로 엮는 스킬이다. 설계 공유 문서의 목적과 같으므로 조사와 서술 양쪽에 쓴다. 스킬 파일은 다음으로 찾고, 버전이 여럿이면 마지막 줄(가장 높은 버전)을 쓴다:

```bash
ls "$HOME"/.claude/plugins/cache/cursor-plugins/pstack/*/skills/{teach,how,why}/SKILL.md 2>/dev/null | sort -V
```

세 스킬 파일과 `<pstack>/docs/harness/claude-code.md`(Cursor 이름을 Claude Code 이름으로 바꾸는 대응표)를 **읽고 그대로 따른다**. Claude Code 의 `Skill` 도구는 pstack 스킬을 거부하고, 세 스킬은 `disable-model-invocation` 이라 모델이 스스로 꺼내지 못한다. 이 단계가 그 호출을 대신한다. pstack 이 없으면 이 블록을 건너뛰고, 건너뛴 사실을 사용자에게 알린다.

1. **방향 잡기(`teach` 1번)**: 독자가 이 문서를 읽고 이해해야 할 것을 2~4개로 정한다. 기준은 비즈니스 담당자가 알아야 하는 것이다. 이 목록이 2단계 본문 절의 뼈대가 된다.
2. **`how` 와 `why` 를 한 메시지에서 병렬로 실행한다(`teach` 2번)**:
   - `how`: 질문은 "이 브랜치가 바꾼 <서브시스템>은 어떻게 동작하나". 범위는 변경 파일과 그 호출 경로다. 변경이 모듈 하나에 그치면 `how` 의 단순 경로(explainer 1개)를, 여러 파일·서비스에 걸치면 복합 경로(explorer 2~4개 → explainer 1개)를 쓴다. 서브에이전트는 `subagent_type: "Explore"`, 모델은 `~/.claude/rules/pstack-models.md` 의 `how explorer`·`how explainer` 줄을 따른다(`opus xhigh` → `model: "opus"`, `effort: "xhigh"`; `inherit-parent`·`auto` 면 `model` 생략).
   - `why`: 질문은 "이 설계 결정을 왜 이렇게 했나". `teach` 의 지시대로 범위를 좁혀서 요청한다. 증거 범주는 소스 관리(git log·`gh pr view`)와 긴 문서(노션 MCP, 레포 밖에 설계 스펙 문서가 있으면 사용자에게 받은 그 경로) 두 가지로 한정하고, 나머지 범주는 `why` 의 계약대로 「건너뜀」으로 기록하게 한다. 설계 스펙과 PR 본문이 이미 있으면 그 경로를 코드 앵커에 넣어 준다. 조사 서브에이전트는 MCP 가 필요하므로 `subagent_type: "general-purpose"` 로 띄우고, 브리프에 "아무것도 쓰지 않는다" 를 넣는다. 모델은 `why investigators`·`why synthesizer` 줄을 따른다.
3. **결과를 2단계 재료로 나눈다**:

   | 결과 | 들어가는 자리 |
   |---|---|
   | `how` 의 Overview·How It Works | 「구성과 선택지」·「동작 흐름」 본문(일상어로 다시 쓴다)과 그림 ①② |
   | `how` 의 Key Concepts | 「용어」 표 |
   | `how` 의 Where Things Live·Gotchas | 「개발자 참고」 토글의 파일 역할 표, 「알아 두어야 할 동작 변화」 |
   | `why` 의 What We Found(인용이 붙은 근거) | 「왜 만들었나」, 「개발자 참고」의 설계 결정 |
   | `why` 의 추론·경쟁 가설·모르는 것 | 본문에 옮기지 않는다. 설계 결정에 꼭 필요하면 `why` 가 쓴 확신 표현을 그대로 유지해서 「개발자 참고」에만 둔다 |

4. `how`·`why` 결과에 나온 사실은 소스에서 한 번 더 확인한 뒤에 쓴다. 서브에이전트 보고는 틀릴 수 있다.

`teach` 의 지시 가운데 이 스킬이 다르게 적용하는 것은 세 가지다. 첫째, 그림은 mermaid·이미지 생성 도구가 아니라 diagram-design PNG 로 그린다. 둘째, 문장은 `unslop`(영어 기준)이 아니라 `~/.claude/KOREAN.md` 를 따른다. 셋째, 문서는 대화가 아니므로 `teach` 4번의 「사람이 없는 1회 실행」 방식으로 완결된 설명을 쓰고, 더 깊은 내용은 「개발자 참고」 토글이 맡는다.

### 2단계: 설계 공유 문서 작성

#### 독자와 문체

- 기본 독자는 제품·사업 담당자다. 이 독자가 코드를 모른 채 "무엇이 달라졌고, 왜 만들었고, 어떻게 동작하는지"를 이해해야 한다.
- 본문은 `teach` 의 설명 순서를 따른다. 각 절은 「이것이 무엇인가」를 한두 문장의 평이한 정의로 시작하고, 그 다음에 이 결과물에서 어떻게 쓰이는지를 잇고, 동작과 이유를 차례로 쌓는다. 동작은 사용자가 실제로 하는 행동을 따라가며 설명한다(「질문을 입력한다 → 모델을 고른다 → 답변이 나온다」). 함수와 상수를 나열하는 것은 참조 자료이지 설명이 아니다.
- 「핵심은」, 「한마디로」, 「요점은」 같은 틀 문구를 쓰지 않는다. 비유나 예고 대신 구체적인 동작 방식을 바로 쓴다.
- 본문에는 함수·클래스·파일·변수 이름을 쓰지 않는다. 예외는 운영 담당자가 직접 만져야 하는 설정 이름뿐이고, 그것도 「현재 상태와 남은 일」 절에 2개 이내로 둔다.
- 한 용어는 한 뜻으로 쓴다. 처음 나오는 용어는 「용어」 표에서 풀이한다(5개 이내). 예: 공유 링크, 만료 기간, 링크 관리자.
- 개발자용 상세(모듈 관계도, 설계 결정, 파일 역할, 검증 수치, 커밋)는 본문 맨 아래 `<toggle heading="h3">개발자 참고</toggle>` 한 곳에 모은다. 본문 중간에 코드 설명을 끼우지 않는다.
- 날짜는 환경의 현재 날짜를 쓴다. 한국어로 쓴다. 사용자에게 한국어 작성 지침(`~/.claude/KOREAN.md` 등)이 있으면 그것을 따른다.

#### 문서 구조

아래 구조를 기본으로 한다. 결과물 성격에 맞게 선택 절은 빼거나 이름을 바꿀 수 있다. 필수 절과 토글은 뺄 수 없다.

```
[태그] 결과물 한 줄 제목 (YYYY-MM-DD)
<callout> 한 줄 요약: 누가 무엇을 할 수 있게 되었나

### 무엇이 달라졌나            ← 필수. 사용자 화면·업무에서 보이는 변화. 화면 요소는 말로 설명한다
### 왜 만들었나                ← 필수. 배경과 목적 2~4문장
### 구성과 선택지              ← 필수. 그림 ①(구성 요소와 역할) + 비교 표 + 용어 표
### 동작 흐름                  ← 필수. 그림 ②(요청이 처리되는 길) + 번호 단계 설명
### 조립 과정                  ← 선택. 그림 ③(설정·선택이 결과물로 조립되는 흐름). 구성 요소의 조합 규칙이 설계 포인트일 때
### 알아 두어야 할 동작 변화    ← 필수. 기존 사용자가 겪는 차이, 제한, 기본값
### 안정성·운영 관점            ← 선택. 재시도·한도·장애 대응. 분기가 있으면 그림
### 확장과 다음 단계            ← 선택. 설계만 된 것은 "설계/후속"으로 표시
### 현재 상태와 남은 일         ← 필수. 배포 상태, 환경 설정, 남은 작업, PR·이슈 링크
<toggle heading="h3">개발자 참고</toggle>   ← 필수
   그림 ④(모듈 관계도, 파일 경로 라벨) · 핵심 설계 결정 · 파일 역할 표 · 검증(테스트 수) · 커밋 목록
```

#### 그림 규칙

그림은 전부 `diagram-design` 스킬로 그려 PNG 로 첨부한다. 최소 구성은 본문 그림 2종(구성, 동작 흐름) + 개발자 참고 그림 1장(모듈 관계도)이다. 본문 그림 1종은 아래 「쌓아 올린다」 규칙에 따라 여러 장이 될 수 있다.

| 보여 줄 것 | diagram-design 타입 | 자리 |
|---|---|---|
| 구성 요소와 역할, 선택지별 팀 구성 | architecture (선택지는 zone 으로 구분) | 구성과 선택지 |
| 요청이 처리되는 단계 | process | 동작 흐름 |
| 시간순 메시지 교환 | sequence | 동작 흐름 |
| 설정·선택이 결과물로 조립되는 단계 | architecture 또는 process | 조립 과정 |
| 조건 분기, 재시도 | flowchart | 안정성·운영 관점 |
| 모듈·파일 관계 | architecture (파일 경로 라벨) | 개발자 참고 |

라벨 규칙:
- 본문 그림의 라벨은 일상어다(공유 링크, 만료 기간 7일, 링크 관리자). 코드 이름은 개발자 참고 그림에만 쓴다.
- 한글 라벨은 12px sans(`'Geist', 'Noto Sans KR', 'Apple SD Gothic Neo', sans-serif`)에 16px 마스크, 라틴 식별자만 Geist Mono 9px, zone 라벨은 7px mono.
- 노드 9개·화살표 12개를 넘으면 두 장으로 나눈다.
- **본문 그림은 쌓아 올린다(`teach` 5번)**: 움직이는 요소가 3개 이상인 본문 그림(구성, 동작 흐름, 조립 과정)은 한 장에 전부 그리지 않는다. 2~3장의 연속 그림으로 그리고, 각 장은 앞 장을 그대로 다시 그린 뒤 요소를 하나(또는 한 묶음) 더한다. 새로 더한 요소에만 accent 를 준다. 각 장 아래에 그 장에서 더한 것을 설명하는 문단을 둔다. 파일 이름은 `<name>-1.html`, `<name>-2.html` 순서로 짓는다.
- 「개발자 참고」의 모듈 관계도는 참조 자료이므로 한 장으로 그린다.
- accent 는 한 장에 1~2개 노드만.
- 제품·구성 요소의 이름은 사용자에게 보이는 이름으로 통일한다. 팀이 정한 표기가 있으면 그것을 쓴다.

절차:
1. `Skill(diagram-design:diagram-design)` 을 로드하고 타입 레퍼런스(architecture/process/sequence/flowchart)를 읽는다. 브랜드 프로필(`~/.diagram-design/profiles/<이름>.md`)이 있으면 그 토큰(paper·ink·muted·accent·link, 제목·본문 폰트)을 HTML `:root`/SVG 에 **직접** 넣는다. 없으면 diagram-design 기본 토큰을 쓴다. 레포에 `.diagram-design` 마커는 두지 않는다.
2. HTML 원본은 재생성용으로 **`~/.diagram-design/out/<페이지 슬러그>/`** 에 저장한다(스크래치패드는 세션과 함께 사라진다). `python3 <diagram-design skill dir>/scripts/self_check.py <html>` 을 통과시킨다. 템플릿 CSS 를 그대로 쓰면 브라우저에서 그림 위쪽이 잘리므로 세 곳을 바꾼다: `body` 에서 `display:flex`·`align-items` 를 빼고, `.frame { max-width:1200px; width:100%; margin:0 auto; }`, `svg { width:100%; height:auto; max-height:calc(100vh - 11rem); display:block; }`(`min-width` 제거).
3. PNG 추출은 번들 스크립트로 한다. 스크립트는 ego-browser 로 HTML 을 `file://` 주소로 직접 열고 `<svg>` 영역만 가로 2400px 로 찍는다. 로컬 서버를 띄우거나 레포 안에 파일을 만들 필요가 없다.
   ```bash
   bash "<이 스킬의 base 디렉터리>/scripts/export_png.sh" ~/.diagram-design/out/<페이지 슬러그>/<name>.html
   ```
   PNG 는 HTML 과 같은 자리에 같은 이름으로 저장된다. 둘째 인자로 저장 경로를, 셋째 인자로 가로 픽셀 수를 바꿀 수 있다.
4. **PNG 를 첨부 전에 사용자에게 먼저 보여 승인 받는다**(Read 로 이미지 표시).
5. 첨부: `notion-create-file-upload {filename}` → 응답 `upload_url` 에 multipart/form-data POST(필드명 `file`, `upload_headers` 전부 포함, 약 10분 만료) → 응답 `suggested_markdown` 의 `<image src="file-upload://…">캡션</image>` 을 본문에 넣는다. 캡션도 일상어로 쓴다.

#### 사실 기반과 상태 표기

- 커밋 메시지만으로 쓰지 않는다. 관련 소스(모듈 docstring, 조립·파이프라인 코드, 설계 스펙 문서)를 직접 읽어 실제 구성·분기·데이터 흐름을 확인한 뒤 쓴다. 모르면 적지 않는다.
- 아직 구현 중이거나 설계만 확정된 부분은 "설계/후속"으로, 미커밋 변경(`UNCOMMITTED`)은 "진행 중"으로 표기한다.
- 「현재 상태와 남은 일」에는 배포된 환경, 환경 설정이 코드 기본값을 덮는 곳(`gh variable list --env <env>` 로 확인), 남은 운영 작업을 적는다.

### 3단계: 노션 페이지 찾기

노션 MCP(`plugin:Notion:notion`)의 `notion-search` 로 인덱스 페이지를 검색해 찾는다.

- 노션이 아직 인증되지 않았다면 MCP 가 안내하는 OAuth URL 을 사용자에게 전달해 브라우저에서 승인하도록 한다. 리다이렉트가 실패하면 주소창 전체 URL 을 받아 인증을 마무리한다.
- **인덱스 페이지는 작업별 하위 페이지가 쌓이는 페이지다** (예: "[BE] …", "[PoC] …"). 본문에는 기존 작업 하위 페이지 링크들이 들어 있다.
- 워크스페이스에 비슷한 이름의 페이지가 사람마다 있으면 검색 결과가 여럿이다. **제목이 정확히 일치하는 것**을 고른다. 애매하면 추측하지 말고 사용자에게 URL 을 확인한다.
- 사용자가 처음부터 페이지 URL/ID 를 줬다면 검색을 건너뛴다.

### 4단계: 쓰기 전 미리보기 + 확인 (중요)

노션 쓰기는 **되돌리기 번거로운 외부 쓰기**다. 실제로 만들기 전에 2단계 본문과 PNG 전부를 사용자에게 보여 주고 승인을 받는다:

> "<인덱스 페이지 이름>" 아래에 다음 하위 페이지를 만듭니다. 진행할까요?
> (미리보기)

사용자가 수정 요청을 하면 반영 후 다시 확인한다. 명시적 승인 전에는 노션에 쓰지 않는다. 본문 초안은 스크래치패드에 `.md` 로 두고, 승인된 판을 그대로 올린다.

### 5단계: 하위 페이지로 생성 (append 아님)

승인되면 **인덱스 페이지의 하위 페이지를 새로 만든다.** 이 페이지는 작업별 하위 페이지가 쌓이는 인덱스이므로, 본문에 블록을 덧붙이는(append) 것이 아니라 **기존 항목들과 똑같이 하위 페이지 한 장으로** 추가한다.

- `notion-create-pages` 사용, `parent` = `{type: "page_id", page_id: <인덱스 페이지 ID>}`.
- 페이지 제목(`properties.title`)은 기존 항목 컨벤션을 따른다. 컨벤션이 없으면 `[<태그>] <한 줄 요약> (YYYY-MM-DD)` 형태로 쓴다(예: `[Feature] 파일 공유 링크: 만료 기간 설정 (2026-01-15)`, `[PoC] …`). 제목은 사용자에게 보이는 기능 이름으로 짓는다. 코드 이름(클래스, enum 값)은 제목에 넣지 않는다.
- 본문 맨 위에 한 줄 요약을 콜아웃(`<callout icon="…">`)으로 두고, `### 헤딩` 으로 구획을 나눈다. 그림은 전부 `<image src="file-upload://…">캡션</image>`, 개발자 상세는 `<toggle heading="h3">개발자 참고</toggle>` 안에 넣는다. 표가 있으면 노션 표를 쓴다. 아이콘(`icon`)을 곁들이면 인덱스에서 눈에 띈다.
  - 노션 마크다운 문법이 불확실하면 추측하지 말고 MCP 리소스 `notion://docs/enhanced-markdown-spec` 을 먼저 읽는다.
  - 노션 도구 인자에 넣는 한글은 UTF-8 글자 그대로 쓴다. `\uXXXX` 이스케이프로 쓰면 16진수 한 자리 오타가 비슷한 다른 글자로 올라간다. 본문은 4단계에서 승인된 `.md` 파일을 Read 해서 그대로 전달하고, 다시 타이핑하지 않는다.
- 절대 부모 페이지 본문을 `replace_content` 로 덮지 않는다(기존 하위 페이지가 삭제될 수 있다). 실수로 본문에 블록을 넣었다면 `update_content` 로 그 구간만 빈 문자열로 치환해 되돌린다.
- 생성 후 `notion-fetch` 로 다시 읽어 그림 수·토글·mermaid 0건을 확인하고, 사용자에게 새 하위 페이지 링크를 알려준다.
  - `notion-fetch` 는 약 20KB 를 넘는 페이지의 뒷부분을 잘라서 돌려준다. 맨 아래에 있는 「개발자 참고」 토글이 보이지 않으면 없다고 판단하지 말고, 자기치환 프로브로 확인한다: `notion-update-page` 의 `update_content` 에 `old_str` 과 `new_str` 을 같은 문자열로 넣는다. 성공하면 그 문자열이 정확히 한 번 있고, `No matches found` 오류면 없다. 오류일 때는 아무것도 쓰이지 않는다.
  - 쓰기 직후의 `notion-search` 결과는 블록별로 늦게 갱신되므로 검증에 쓰지 않는다.

### 6단계: 기존 페이지 갱신

같은 페이지를 다시 고칠 때(사용자가 "다시 써", "고쳐", "비개발자용으로 바꿔" 라고 할 때) 지키는 것:

- 사용자가 이미 승인한 그림은 본문의 그 자리에 그대로 둔다. 설명 문단과 캡션만 바꾼다. 토글로 내리거나 새 그림으로 바꾸려면 먼저 묻는다. 승인된 그림은 2단계 라벨 규칙의 적용 대상이 아니다. 라벨이 코드 이름이어도 그대로 두고, 캡션과 설명 문단을 일상어로 쓴다.
- 본문 전체 교체는 `notion-update-page` 의 `replace_content` 로 한다. 기존 `<image>` 는 fetch 결과의 `notion-file-block://…` 주소를 그대로 다시 넣는다.
- `replace_content` 는 기존 `<image>` 블록의 캡션을 바꾸지 않는다. 캡션은 `update_content` 의 old_str/new_str 로 따로 바꾼다.
- 본문에 ```mermaid 블록이 남아 있는 옛 문서는 `diagram-design:import-mermaid` 로 다시 그려 PNG 로 바꾸고, 블록 전문을 old_str 로 삼아 `<image>` 태그로 치환한다.
- 제목은 `update_properties` 로 바꾼다.
- 갱신 뒤에도 5단계와 같은 방법(`notion-fetch` + 자기치환 프로브)으로 확인한다.

## 예시

**입력(사용자):** "이번 브랜치 작업한 거 노션 Task 현황에 정리해줘"

**스킬 동작:**
1. `gather_branch_work.sh` 실행 → `feat/share-link-expiry`, base `origin/main`, 커밋 12개. 이어서 `teach` 절차로 `how`(복합 경로)와 `why`(git·gh·노션으로 한정)를 병렬 실행하고, 결과를 소스·스펙과 대조.
2. 설계 공유 문서 작성(비즈니스 독자 기준):
   ```
   [Feature] 파일 공유 링크: 만료 기간 설정 (2026-01-15)
   <callout> 파일을 공유하는 사람이 링크가 언제까지 열리는지 정할 수 있다.

   ### 무엇이 달라졌나
   - 공유 창에 「만료 기간」 선택 상자가 생겼다. 만료된 링크를 열면 안내 화면이 나온다.
   ### 왜 만들었나
   - 한 번 만든 링크가 계속 열려 있었다. 외부에 보낸 파일을 기간이 지나면 닫을 방법이 필요했다.
   ### 구성과 선택지
   - (PNG architecture 2장, 쌓아 올리기) 1장: 공유하는 사람 → 공유 링크. 2장: + 만료 기간과 링크 관리자 + 비교 표 + 용어 3개
   ### 동작 흐름
   - (PNG process 3장, 쌓아 올리기) 1장: ① 만료 기간을 고른다 → ② 링크를 만든다. 2장: + ③ 받은 사람이 링크를 연다 → ④ 기간을 확인한다. 3장: + ⑤ 파일 또는 만료 안내를 보여 준다
   ### 알아 두어야 할 동작 변화
   - 기존 링크는 만료되지 않는다. 새로 만드는 링크의 기본 만료 기간은 30일이다.
   ### 안정성·운영 관점
   - (PNG flowchart) 만료 시각이 지난 링크는 하루에 한 번 정리한다. 정리에 실패하면 다음 날 다시 시도한다.
   ### 현재 상태와 남은 일
   - main 머지 완료. 운영 환경의 기본 만료 기간 설정이 아직 비어 있어 코드 기본값 30일이 적용된다.
   <toggle heading="h3">개발자 참고</toggle>
   - (PNG 모듈 관계도) · 설계 결정 4항 · 파일 역할 표 · 검증 · 커밋 12개
   ```
3. 인덱스 페이지 검색 → 발견
4. PNG 전부와 본문 미리보기 제시 → 사용자 승인
5. 그 페이지의 하위 페이지로 한 장 생성 → fetch 로 확인 → 링크 회신

## 주의사항

- **사실만**: 커밋/diff 에 없는 내용을 지어내지 않는다. 불확실하면 사용자에게 묻는다.
- **`teach`·`how`·`why` 가 기본 절차다**: 1단계에서 세 스킬을 돌리고, 본문은 `teach` 의 설명 순서로 쓴다. 결과는 소스로 확인한 뒤에만 적는다. `why` 의 확신 표현은 바꾸지 않는다. pstack 이 없으면 그 사실을 알리고 1단계 수집만으로 쓴다.
- **하위 페이지로**: 본문 블록 추가가 아니라 인덱스 페이지의 하위 페이지로 만든다. 부모 본문은 `replace_content` 로 덮지 않는다(기존 하위 페이지 보존).
- **확인 우선**: 노션 쓰기 전 미리보기·승인은 생략하지 않는다. PNG 도 첨부 전에 보여 준다.
- **베이스 브랜치**: 기본 `develop`. 레포에 develop 이 없을 수 있으니 스크립트의 자동 탐색 결과(`BASE`)를 사용자에게 한 번 알려 준다.
- **브라우저는 ego-browser 만**: 그림을 눈으로 확인하거나 PNG 로 뽑을 때 Playwright MCP 와 claude-in-chrome 을 쓰지 않는다.
- 시크릿/토큰이 diff 에 보이면 노션 본문에 넣지 않는다.
