# PR 리뷰

## 개요

PR 하나를 5축으로 검토한다. "문제"로 적는 것은 PR head 에서 재현한 것뿐이다. 결과는 HTML 보고서(Artifact 도구가 있으면 발행, 없으면 로컬 파일) + PR 코멘트 초안이고, 게시는 사용자 승인 뒤에만 한다.

| 축 | 질문 | 증거 |
|---|---|---|
| 크리티컬 | 범위·권한·데이터가 새는가. 상태가 교착하는가. 예외 경로가 run 을 죽이는가 | 재현 테스트 통과 로그 |
| 중복 코드 | 같은 본문이 두 곳에 있는가 | 두 코드 조각 나란히 + `scripts/dupcheck.py` 수치 |
| 미재사용 | 기존 헬퍼가 있는데 새로 썼는가. private 이름을 밖에서 쓰는가 | 기존 함수 위치 + 새 함수 위치 |
| 아키텍처 | import 계약, 포트 소유권, 프레임워크 도메인 무지, 미들웨어 자리, 어휘 결합 | 계약 검사 명령의 출력 + 규칙 원문 인용 |
| 구조 진단 | 어떤 설계 결정 하나가 결함 여럿을 같이 만들었나. 근본 수정과 증상 패치는 무엇인가 | 4단계 경로 지도 + 확인된 결함 2건 이상(재현 또는 코드 대조) + 위반한 규칙 원문 + 레포에 이미 있는 대안 자리 |

축 밖의 점검이 둘 더 있다. **안전 사실 증명**(4·6단계, 규칙 14)은 "문제 없음" 쪽의 증거이고, **PR 테스트 점검**(5단계)은 PR 이 가져온 테스트가 무엇을 증명하는지 변이 실행으로 확인한다. 둘의 결과는 8절 검증 표와 마이너·메이저 항목으로 들어간다.

## 입력

**인자:** $ARGUMENTS

- 받는 형태: `/review-pr 2008`, `/review-pr https://github.com/<owner>/<repo>/pull/2008`, 또는 대화 속 PR 번호·링크. 대상 레포는 세션 디렉터리의 레포다(`gh repo view --json nameWithOwner --jq .nameWithOwner`). 링크의 레포가 그것과 다르면 먼저 묻는다.
- URL 이면 `/pull/` 뒤의 숫자가 `N` 이다. 번호도 링크도 없으면 먼저 묻는다.
- 아래 모든 명령의 `N` 은 그 번호이고, `prN` 은 `pr2008` 처럼 쓴다.

## 플러그인 사전 고지 (선택)

이 스킬이 쓰는 플러그인은 pstack 하나다. 없어도 리뷰는 끝나고, 적대 리뷰 후보 소스와 UI 의 TS 규칙 표만 빠진다. blast-radius·correct·원칙 스킬(test-behavior-not-implementation·boundary-discipline·minimize-reader-load·migrate-callers-then-delete-legacy-apis)에서 가져온 절차는 이 문서에 요약돼 있어 플러그인이 없어도 된다. 리뷰를 시작할 때 설치 여부를 확인해 채팅 첫 줄에 한 번 알린다.

| 플러그인 | 쓰는 곳 | 없을 때 | 설치 |
|---|---|---|---|
| pstack (`interrogate`, `typescript-best-practices`) | 3단계 적대 리뷰 후보 수집 · UI 리뷰의 TS 규칙 표 | 건너뛰고 후보 처리표 머리에 "interrogate: 미설치", TS 규칙 표는 생략 | `/plugin marketplace add cursor/plugins` → `/plugin install pstack@cursor-plugins` → `/pstack:setup-pstack` |

확인: `ls "$HOME"/.claude/plugins/cache/cursor-plugins/pstack/*/skills/interrogate/SKILL.md 2>/dev/null | sort -V | tail -1` 이 비면 미설치다. `gh`·`git`·`python3` 는 필수다. 그 밖의 도구(테스트 러너·린터·패키지 관리자)는 대상 레포의 개발 환경을 따른다.

Codex CLI(`command -v codex`)는 선택 도구다. 있으면 3단계 적대자 하나를 `codex exec` 로 돌려 다른 모델 계열의 관점을 얻는다. 없으면 적대자는 전부 Claude 서브에이전트다. 설치 여부를 pstack 과 함께 채팅 첫 줄에 알린다.

## 용어

| 용어 | 뜻 |
|---|---|
| 크리티컬 | 범위·권한·데이터 누출, run 사망, 교착. 재현 필수 |
| 메이저 | 기능이 지시문·docstring·계약·연결 이슈의 인수 조건대로 동작하지 않음. 재현 필수 |
| 마이너 | 그 밖의 결함. 재현 또는 코드 대조 |
| 중복 / 미재사용 / 아키텍처 | 축 이름이 곧 라벨. 심각도를 매기지 않는다. 증거는 코드 대조·계약 검사 |
| 관찰 | 동작은 확인했으나 문제인지 판단할 근거가 모자란 것, 이 PR 의 결함이 아닌 것, 또는 저자·제품 결정으로 결함에서 내린 것. 판정 수에 세지 않는다 |
| 판정 | 셋 중 하나. **머지 가능** / **머지 전 수정 필요**(크리티컬·메이저가 1건 이상) / **구조 재검토 필요**(근본 수정이 PR 범위를 넘는 구조 원인이 있고 증상 패치를 권하지 않을 때) |
| 판정 수 | 카운트 타일에 세는 수 — 구조 원인·크리티컬·메이저·중복·미재사용·아키텍처·마이너. 관찰·"재사용을 잘한 곳"은 세지 않는다 |
| 확인 방법 chip | `재현됨`(재현 테스트) · `코드 대조`(두 코드 나란히) · `git 대조`(커밋 이력, PR 본문 vs diff) · `계약 검사`(프로필의 계약 검사 명령·가드 테스트 출력) · `결정으로 내림`(저자 답글 또는 제품 결정으로 관찰로 내린 것. 출처를 함께 적는다 — 코멘트 ID, 또는 결정 날짜와 결정자 역할) · `이전 리뷰 유지`(재리뷰에서 새 head 에 그대로인 이전 항목) · `기존 실패`(base 에서도 실패하는 테스트. 판정 수에 세지 않는다) · `변이 실행`(PR 의 테스트가 지키는 동작을 일부러 깨뜨리고 돌려도 통과함을 보인 로그. 테스트 결함의 증거) · `확신 n/5`(chip 이 아니라 8절 표 셀과 판정 상자에 글자로 적는 표기. 안전 사실과 해소한 위험에 붙는 blast-radius 사다리 단계 — 1 말했다 · 2 줄을 가리켰다 · 3 실패 경로가 닿지 않음을 보였다 · 4 실제 코드로 돌렸다 · 5 앱에서 재현했다. 3 이하는 「확인하고 해소한 위험」에 넣지 않는다) |
| 유사도 | `scripts/dupcheck.py` 가 잰 difflib ratio — `autojunk=False`, 줄 앞뒤 공백·빈 줄·줄 끝 주석 정규화. 0.9 이상 "복사본", 0.6 이상 "부분 공유"(최장 공통 구간 길이를 함께 적는다), 그 아래는 중복으로 세지 않는다. 손으로 쓴 `SequenceMatcher` 호출은 쓰지 않는다 — 기본값 `autojunk=True` 는 200자 넘는 조각을 낮게 잰다(같은 쌍이 0.504 vs 0.694) |
| 규칙 원문 | 문서 규칙(`ARCHITECTURE.md`·`CLAUDE.md`·계약 설정 파일의 주석), 코드에 적힌 계약(docstring·주석·기존 경로가 지키는 불변식), 또는 PR 이 `Refs`/`Closes` 로 연결한 이슈의 인수 조건. 전부 파일:줄 또는 이슈 번호·절로 가리킨다. **적용 범위를 먼저 확인한다** — 그 규칙이 지금 보는 계층·객체에 대한 것인가(예: 프레임워크 그래프 상태의 append-only 규칙은 메시지 스냅샷 규칙이 아니다) |
| 국소 결함 | 구조 원인에 속하지 않는 결함. 심각도대로 2절 또는 5절에 두고 라벨만 단다 |
| 인라인 대상 | **크리티컬·메이저만** 인라인 코멘트를 단다. 마이너·중복·미재사용·아키텍처·관찰은 보고서와 요약 리뷰 표에만 적는다 — 인라인이 많으면 고쳐야 할 것이 묻힌다 |
| 결정 기록 | 제안 한 줄마다 붙는 근거 묶음(아래 "결정 기록" 절의 6항). 제안을 정하는 순간 `$S/prN-decisions.md` 에 항목 chip 별로 적고, HTML 보고서의 접힌 상자 「제안 근거」로만 내보낸다. PR 코멘트에는 싣지 않는다 |
| Artifact 없는 환경 | 도구 목록에 `Artifact` 가 없는 세션(Codex 등). 보고서 HTML 은 같은 템플릿으로 같은 모양을 만든다. 다른 점은 발행 URL 유무뿐이다 — 9단계 발행, 10단계 링크 박스·링크 전용 코멘트를 생략하고 HTML 은 `$S` 의 로컬 파일로 두어 브라우저로 연다. Markdown 으로 올리지 않는다 |
| 세션 디렉터리 `$W` | 이 세션(Claude Code 또는 Codex)의 작업 디렉터리(사용자의 체크아웃). `git rev-parse --show-toplevel` |
| PR head worktree | `$S/prN-wt`. 점검·재현·기계 검증은 여기서 돌린다. 3단계 적대자 worktree `$S/prN-adv-<k>` 는 적대자만 쓰고, 그 재현 파일은 이름을 바꿔 여기로 복사한 뒤 다시 돌린다 |
| 스킬 폴더 `$SK` | 이 스킬의 base 디렉터리. 스킬을 실행할 때 알려 주는 경로를 `SK=<경로>` 로 적는다. 템플릿 `report-template.html`, 도구 `scripts/dupcheck.py`·`scripts/check-report.py`·`scripts/check-inline-lines.py`, 게시 절차 `reference/publish.md` 가 있다 |
| 레포 프로필 | 레포마다 다른 값(서브트리·테스트 러너·검증 명령·규칙 문서)을 적은 표. 아래 "레포 프로필" 절. `$W/.claude/review-pr.md` 가 있으면 그것을 읽고, 없으면 1단계에서 조사해 `$S/prN-profile.md` 에 쓴다 |
| 서브트리 `<sub>` | 변경 파일이 속한 패키지 디렉터리. 매니페스트(`pyproject.toml`·`package.json` 등)가 있는 가장 가까운 상위 디렉터리다. 단일 패키지 레포면 `.` 이다 |
| 기본 브랜치 | 레포의 기본 브랜치. `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` |
| 재리뷰 | 같은 PR 에 이전 리뷰(내 `$S` 산출물, GitHub 의 이전 리뷰, 다른 세션의 보고서)가 있을 때. 아래 "재리뷰" 절을 1~10단계에 겹쳐 적용한다 |
| 후보 처리표 | `$S/prN-candidates.md`. code-review·리뷰 봇·이전 리뷰에서 온 후보마다 출처 · 후보 한 줄 · 처리(반영 항목 ID / 기각 이유 / 관찰 ID). 보고서 8절에 옮긴다 |
| 게시 기록 | `$S/prN-published.json`. 게시 턴이 적는 head sha · 리뷰 id · 인라인 리뷰 id 목록 · 링크 코멘트 id. 재리뷰의 PUT·PATCH·DELETE 는 이 파일의 id 를 쓴다 |

## 절대 규칙

1. **짐작으로 "문제"를 적지 않는다.** 크리티컬·메이저 후보는 전부 재현 테스트를 돌린다. 재현 안 된 것은 관찰로 내리거나 지운다.
2. 중복·미재사용은 런타임 재현 대신 두 코드를 나란히 보여 준다. 유사도는 `python3 "$SK/scripts/dupcheck.py"` 로 잰다.
3. 코드를 고치지 않는다. 레포에 파일을 커밋하지 않는다. 재현 테스트는 PR head worktree(와 3단계 적대자 worktree)에만 두고 산출물 폴더 `$S`로 복사한다. 예외는 하나다 — 5단계 PR 테스트 점검의 변이는 PR head worktree 안에서 넣고 그 테스트만 돌린 뒤 즉시 되돌린다. `$W`(세션 체크아웃)는 어떤 경우에도 바꾸지 않는다.
4. **GitHub 에 쓰지 않는다.** 코멘트는 초안 파일까지만 만든다. 게시는 사용자가 승인한 뒤 별도 턴에서, `gh` 로만 한다.
5. 구조가 틀렸으면 그렇게 말한다. 국소 패치만 나열해 구조 문제를 숨기지 않는다. 근본 수정과 증상 패치를 둘 다 적고 어느 쪽인지 표시한다.
6. 구조 진단도 증거 규칙을 따른다. 확인된 결함 2건 이상(재현 또는 코드 대조로 확인한 것 — 중복·미재사용도 센다) + 위반한 규칙 원문 + 레포의 대안 자리. 셋 중 하나라도 없으면 원인이 아니라 관찰이다. 결함 1건으로는 원인을 세우지 않는다 — 그 분석은 해당 항목의 제안에 적는다.
7. 답변·보고서·코멘트는 한국어, ASD-STE100 규칙(짧은 문장, 능동태, 한 용어 한 뜻, 장식어 없음).
8. 이식성: 어느 팀원의 Claude Code·Codex 환경에서도 같은 결과가 나와야 한다. 특정 사용자 이름이 박힌 경로를 쓰지 않는다(`$HOME`·`$S` 같은 변수는 된다). gist·Pages·Notion 링크, 브라우저 자동화 첨부, Markdown 전체 보고서 코멘트는 쓰지 않는다.
9. Bash 호출 사이에 셸 변수는 남지 않는다. `S`·`B`·`W`·`BASE` 는 쓰는 호출마다 다시 정의하거나 한 호출에 묶는다.
10. **근본 수정 제안도 재현 대상이다.** 제안이 바꾸려는 경로(이벤트 → 누적기 → 저장 → 전파, 델타인가 스냅샷인가, 누가 소비하는가)를 4단계 지도에서 파일:줄로 확인한 뒤에만 적는다. 확인하지 않은 제안은 적지 않는다. 주장의 중간 고리("그 이벤트가 어디로 가는가")도 코드 줄로 확인한다.
11. **모든 제안은 적합성을 확인한 뒤 적는다.** 구조 판정의 근본 수정만이 아니라 항목마다 붙는 "제안" 한 줄도 같다. (a) 제안이 가리키는 함수·파일·인자·설정이 실제로 있는지 `rg` 로 확인한다 (b) 4단계 지도의 구간·단위와 맞는지 — 그 자리에서 그 값을 읽을 수 있는지, 그 계층이 그 일을 해도 되는지(계약 검사·포트 소유권) (c) 제안이 결함을 실제로 없애는지 말로 검증한다. 셋 중 하나라도 확인하지 못하면 제안을 적지 않고 결함만 적는다. 확인한 결과는 그 자리에서 결정 기록에 적는다(아래 "결정 기록" 절). 결정 기록이 없는 제안은 보고서에 적지 않는다.
12. **산출물에 추측을 두지 않는다.** 보고서·요약·인라인·채팅 답변 어디에도 "~수 있다"·"~예상된다"·"~로 보인다"·"아마"·"가능성" 으로 끝나는 결과 주장을 두지 않는다. 결과를 확인하지 못했으면 그 문장을 지우고 확인한 사실까지만 적는다. 조건부 결함("X 이면 Y")은 X 가 코드에 실제로 있는 분기임을 파일:줄로 보일 때만 적는다. 내보내기 전에 산출물 전체(결정 기록 포함)를 그 표현으로 검색한다(10단계).
13. **로그는 원문이다.** 재현·기계 검증 로그는 요약·필터 도구를 거치지 않은 출력으로 저장한다. 출력 요약 훅(rtk 등)이 있는 환경이면 `rtk proxy <명령>` 처럼 원문을 내는 호출로 저장한다. 요약 한 줄과 사용자 홈 아래 경로만 남은 로그는 증거가 아니다.
14. **"문제 없음" 도 증거가 필요하다.** 4단계의 안전 사실과 보고서의 「확인하고 해소한 위험」은 blast-radius 사다리 4 이상(실제 코드를 돌린 것)만 적는다. 3 이하는 "미증명(사다리 n)" 으로 적거나 지운다. 그럴듯하게 읽히는 안전성 설명은 참이든 거짓이든 똑같이 설득력 있어 보이므로 글로는 증거가 되지 않는다.

## 절차

순서가 곧 규칙이다. **구조 파악(4)이 축별 점검(5)·재현(6)보다 앞이고, 구조 판정(7)은 재현 뒤다.** 결함을 먼저 모으고 나서 구조를 "설명"하면 결함에 맞춘 이야기를 짓게 된다 — 경로를 먼저 그려 두면 어떤 결함이 구조에서 오고 어떤 제안이 성립하는지가 그 위에서 보인다.

### 1. PR 메타 수집 — 세션 디렉터리

```bash
REPO=$(gh repo view --json nameWithOwner --jq .nameWithOwner)
gh pr view N --json number,title,body,headRefOid,baseRefName,headRefName,files,additions,deletions,state
gh pr checks N
gh api "repos/$REPO/pulls/N/comments" --paginate   # 인라인 코멘트(리뷰 봇 포함)와 저자 답글(in_reply_to_id)
gh api "repos/$REPO/pulls/N/reviews" --paginate
gh api "repos/$REPO/issues/N/comments" --paginate  # 일반 코멘트. 이전 리뷰의 링크 코멘트가 여기 있다
gh pr diff N --name-only
gh pr view N --json body --jq .body | grep -oE '(Refs|Closes|Fixes|Resolves)[^#]*#[0-9]+' | grep -oE '[0-9]+' | sort -u \
  | xargs -I{} gh issue view {} --json number,title,body                       # 연결 이슈. 인수 조건이 계약이다
```

- `baseRefName` 을 `BASE` 로 적어 둔다. 스택 PR 이면 기본 브랜치가 아니다.
- 연결 이슈의 **인수 조건**을 4단계 지도의 규칙·적용 범위에 옮겨 적는다. 메이저 판정의 "계약"에는 이 인수 조건이 들어간다. 연결 이슈가 없으면 그 사실을 지도에 적는다.
- 리뷰 봇(CodeRabbit 등)의 코멘트는 후보 목록이다. 후보마다 `$S/prN-candidates.md` 에 한 줄(출처 · 후보 · 처리는 비워 둠)을 적는다. 내 발견과 겹치면 "<봇 이름> 도 지적" 표시를 단다.
- `gh pr checks` 의 실패는 적어 두고 8단계에서 기존 실패인지 가른다. 여기서 PR 결함으로 적지 않는다.
- 본문의 "변경 사항"을 파일 목록과 대조한다. 본문이 말하는 변경이 diff 에 없으면 `git log origin/$BASE --oneline -- <path>` 로 이미 들어갔는지 확인한다.
- 변경 파일이 속한 서브트리마다 **레포 프로필**을 확정한다(아래 "레포 프로필" 절). 5·6·8단계의 명령은 전부 이 프로필에서 읽는다.
- 산출물 폴더(2단계 `$S`)에 이전 산출물이 있거나 GitHub 에 이전 리뷰가 있으면 **재리뷰**다. 아래 "재리뷰" 절을 지금부터 겹쳐 적용한다.

### 2. 산출물 폴더와 PR head worktree — 세션 디렉터리

```bash
S="${PR_REVIEW_DIR:-$HOME/.pr-reviews}/prN"; BASE=<1단계 baseRefName>
mkdir -p "$S"
git fetch origin "$BASE" "pull/N/head:refs/remotes/origin/pr-N"
[ -d "$S/prN-wt" ] && git worktree remove --force "$S/prN-wt"      # 재리뷰면 이전 worktree 를 비운다
git worktree add "$S/prN-wt" origin/pr-N --detach
B=$(git merge-base "origin/$BASE" origin/pr-N)
git diff "$B"...origin/pr-N -- ':!**/tests/**' > "$S/prN-src.diff"
git diff "$B"...origin/pr-N -- '**/tests/**'   > "$S/prN-tests.diff"
```

`$S` 는 세션이 끝나도 남는다. scratchpad 는 세션 중 사라질 수 있으므로 쓰지 않는다. 재리뷰면 같은 `$S` 를 쓴다 — 덮어쓰기 전에 아래 "재리뷰" 절의 읽기 순서를 먼저 마친다. worktree 에는 설치된 의존성이 없다. 프로필의 「의존성 준비」대로 준비한다.

### 재리뷰 — 이전 리뷰가 있을 때, 1~10단계에 겹쳐 적용

이전 리뷰는 내 `$S` 산출물, GitHub 에 올라간 이전 리뷰(다른 세션·다른 사람 것 포함), 이전 Artifact 셋 중 어느 것이어도 된다. 기억으로 재구성하지 않는다.

1. **읽기 순서** — `$S/prN-published.json`(이전 head·리뷰 id) → `$S/prN-decisions.md`·`$S/prN-review.html`(이전 항목 전부, 관찰 포함) → 1단계에서 받은 이전 리뷰 본문·인라인·저자 답글 → 로컬 보고서가 없으면 `$S/prN-artifact-url.txt` 의 Artifact 를 `read` 한다. 이전 항목은 전부 후보 처리표에 "출처: 이전 리뷰" 로 올린다.
2. **상태표** `$S/prN-rereview.md` — 이전 항목마다 한 줄: ID · 이전 분류 · 새 head 상태(**해소** / **잔존** / **결정으로 내림**) · 확인 방법. 해소 = 이전 재현 테스트가 새 head 에서 실패한다(결함 동작이 사라졌다) 또는 git 대조(고친 커밋 sha). 잔존 = 보고서에 그대로 옮기고 chip `이전 리뷰 유지`. 결정으로 내림 = 저자 답글("의도적")·제품 결정으로 결함에서 내려 6절 관찰로 옮기고 chip `결정으로 내림` + 출처. 이전 관찰도 전부 표에 올린다 — 빠뜨리기 가장 쉬운 것이 관찰이다.
3. **새 발견**은 보통 절차(4~7단계)로 찾는다. 결정으로 내린 항목이 구조 원인의 결함 2건에 들어 있었으면 원인도 다시 센다(규칙 6).
4. **보고서** — 읽기 순서를 마친 뒤 `prN-map.md`·`prN-decisions.md`·`prN-review.html`·초안 세 파일은 새 head 기준으로 덮어쓴다. 덮어쓰기 전에 이전 판본을 `$S/prev-<이전 head 7자>/` 로 옮긴다. 판정 상자 첫 줄에 "재리뷰: <이전 head 7자> → <새 head 7자>". 8절 검증에 상태표를 옮긴다.
5. **게시** — 새 요약 리뷰를 만들지 않는다. `reference/publish.md` 의 재리뷰 명령으로 이전 리뷰 본문 PUT, 해소·내린 항목의 인라인 DELETE, 새 크리티컬·메이저만 새 인라인 리뷰, 링크 코멘트 PATCH 를 한다. id 는 전부 `prN-published.json` 에서 읽는다.

### 3. 후보 수집 — 1단계 직후 바로

`Skill(code-review, args="N high")` 를 **1단계가 끝나는 즉시** 호출한다. 30분 넘게 걸릴 수 있어 늦게 부르면 초안 승인 뒤에 도착한다. 백그라운드 에이전트로 돌고 세션 디렉터리를 쓴다. `--comment`·`--fix` 는 넘기지 않는다. 끝난 뒤 `git -C "$W" rev-parse HEAD` 가 시작 때와 같은지 본다 — code-review 가 세션 체크아웃에 PR 브랜치를 checkout 하고 끝낸 적이 있다(`git checkout --detach <원래 sha>` 로 되돌린다). 도구 목록에 `Skill` 이 없는 환경이면 이 단계를 건너뛰고 후보는 5단계에서 직접 모은다. 결과는 후보다. 도착하면 후보마다 `$S/prN-candidates.md` 에 한 줄을 적는다. 5·6단계에서 직접 확인하기 전에는 보고서에 넣지 않는다. 기각한 후보도 이유와 함께 표에 남긴다 — 다음 리뷰어가 같은 후보를 다시 조사하지 않게 하기 위해서다.

**pstack interrogate(적대 리뷰)** — code-review 호출 직후 같은 턴에 돌린다. 스킬 파일을 찾는다:

```bash
ls "$HOME"/.claude/plugins/cache/cursor-plugins/pstack/*/skills/interrogate/SKILL.md 2>/dev/null | sort -V | tail -1
```

파일이 없으면(pstack 미설치) 이 소스를 건너뛰고 `$S/prN-candidates.md` 머리에 "interrogate: 미설치" 라고 적는다(설치 명령은 「플러그인 사전 고지」 절). 있으면 그 파일과, 같은 플러그인 폴더의 `docs/harness/claude-code.md`(Cursor 이름 → Claude Code 대응표)와 `skills/arena/SKILL.md` 를 읽고, interrogate 가 시키는 대로 arena Phase A 3·4항 → Phase B → Phase F 를 돌린다(Phase C·D·E 는 건너뛴다). Claude Code 의 `Skill` 도구는 pstack 스킬을 거부하고, interrogate 는 `disable-model-invocation` 이라 사용자가 부르지 않으면 모델이 꺼내지 못한다. 이 절차가 그 호출을 대신한다. 이 스킬에 맞춘 대응:

- 범위는 1단계의 PR 본문·커밋 로그와 `git -C "$S/prN-wt" diff "$B"...HEAD` 다. 의도는 PR 본문에서 한 문단으로 적는다(interrogate 의 in-your-own-words 단계). 불분명해도 사용자에게 묻지 않고, PR 본문에 적힌 범위까지만 의도로 둔다.
- 적대자(Phase A 3항)는 `~/.claude/rules/pstack-models.md`(`/pstack:setup-pstack` 이 쓰는 파일)의 `interrogate reviewers` 줄 항목 수만큼 띄운다(파일이나 줄이 없으면 arena 기본값 2명). `subagent_type: "general-purpose"`, `model`·`effort` 는 그 항목을 따른다(`opus xhigh` → `model: "opus"`, `effort: "xhigh"`; `inherit-parent`·`auto` 면 `model` 생략). 적대자마다 자기 worktree(Phase A 4항)를 준다: `git worktree add "$S/prN-adv-<k>" origin/pr-N --detach`. 그 worktree 에도 프로필의 「의존성 준비」를 적용한다. 브리프는 interrogate 의 것을 그대로 쓴다 — "Break this change. Prove each finding with a run against the real code… Report each finding with a title, the exact command, the output it printed, and the output the intent requires. Leave out anything you did not run… No findings is a valid result" — 에 범위·의도·자기 worktree 경로와 "재현 파일은 그 worktree 의 tests/ 아래에만 만들고 다른 파일은 고치지 않는다" 를 붙인다. 모두 한 메시지에서 띄운다(Phase B).
- Codex CLI 가 있으면 적대자 중 마지막 하나(k = 적대자 수)는 서브에이전트 대신 `codex exec` 로 돌린다. 브리프는 같은 것을 stdin 으로 넘기고, Claude 적대자와 같은 턴에 백그라운드로 띄운다. 모델은 리뷰어의 `~/.codex/config.toml` `model` 기본값이고 `-m` 으로 바꿀 수 있다. 출처에 적을 모델 이름은 `-m` 값, 없으면 `python3 -c 'import tomllib,os;print(tomllib.load(open(os.path.expanduser("~/.codex/config.toml"),"rb"))["model"])'` 로 읽는다.

  ```bash
  printf '%s' "$BRIEF" | codex exec -C "$S/prN-adv-<k>" --sandbox workspace-write --ephemeral -o "$S/prN-adv-<k>-codex.md" - 2>&1 | tee "$S/prN-adv-<k>-codex.log"
  ```

  `-o` 파일이 그 적대자의 보고서다. 처리(Phase F 재실행, 후보 처리표, worktree 점검·삭제)는 Claude 적대자와 같다.
- 끝난 뒤 적대자 worktree 마다 `git status --porcelain` 으로 재현 파일 밖의 변경이 없는지 본다. 발견마다 재현 파일을 `$S/prN-wt` 의 같은 디렉터리로 복사하되 이름을 `zz_prN_review_repro_adv<k>_<label>` 이 들어간 이름(Python 은 `test_zz_prN_review_repro_adv<k>_<label>.py`, JS·TS 는 `zz_prN_review_repro_adv<k>_<label>.test.tsx`)으로 바꾼다 — 그래야 8단계 lint 제외와 11단계 복사가 그 파일을 잡는다 — 그리고 적힌 명령을 그 이름으로 다시 돌려(Phase F) 출력이 같고 그 실패가 의도를 깨뜨릴 때만 후보로 남긴다. 같은 원인의 발견은 하나로 합친다.
- 남긴 발견을 후보 처리표에 올린다. 출처는 `interrogate(<적대자 모델>)`(Codex 면 `interrogate(codex <모델>)`) 로 적고, 둘 이상의 적대자가 독립적으로 낸 항목에는 `합의` 를 붙인다. 적대자마다 버린 발견 수와 이유를 표 머리에 한 줄로 적는다(interrogate 의 Dropped). 5·6단계에서는 합의 항목부터 확인한다.
- 규칙 1·4 는 그대로다. interrogate 지적도 6단계 재현 전에는 보고서에 넣지 않는다. 판정은 7단계가 한다. 적대자 worktree 는 11단계에서 `prN-wt` 와 함께 지운다.

### 4. 구조 파악 — PR head worktree

결함을 찾기 전에 바뀐 코드가 놓인 경로를 끝까지 읽는다. 여기서는 "문제"를 적지 않는다. 산출물은 **경로 지도** 한 장(`$S/prN-map.md`)이고, 재현(6)과 구조 판정(7)은 둘 다 이 지도 위에서 한다.

1. 변경이 만드는 데이터·이벤트의 흐름을 **생산 → 소비 → 저장 → 전파 → 표시**까지 파일:줄로 적는다. 예: 작업 단계 이벤트 → 스트림 yield → 실행기의 소비 → 누적기의 append → 스냅샷 저장 → 구독 payload → UI 파서.
2. 구간마다 **단위**를 적는다 — 델타인가 스냅샷인가, 누가 병합하는가, 코얼레싱·잠금이 있는가, 취소·실패 때 누가 마무리하는가.
3. 그 경로에 이미 있는 **불변식·규칙**과 그 **적용 범위**를 적는다 — 기존 경로가 지키는 범위 필터, docstring 계약, 프로필의 「규칙 원문」 문서. 규칙이 다루는 계층·객체가 지금 보는 것과 같은지 확인한다. **변경 파일이 속한 서브트리마다 `$S/prN-wt/<sub>` 의 규칙 문서(`CLAUDE.md`·`AGENTS.md` 등)를 직접 읽는다**(그 파일이 `@` 로 가져오는 파일도 함께). 규칙 문서가 작업별 문서 표로 `docs/*.md` 를 가리키면, 변경과 관련된 문서를 골라 함께 읽는다. worktree 는 세션 디렉터리 밖이라 Claude Code 가 그 문서를 자동으로 로드하지 않는다. 「금지 사항」·「규칙」·「원칙」 절의 문장을 규칙 원문 후보로 지도에 파일:줄과 함께 옮긴다. 서브트리에 규칙 문서가 없으면 그 사실을 지도에 적는다.
4. 기존 경로와 새 경로가 **갈라지는 지점**을 표시한다 — 병렬 arm, 종류별 특수 처리 분기, 기존 보장을 지나지 않는 새 입력.
5. **안전 사실 하나**를 적는다(blast-radius). 위험해 보이는 변경이 안전하다면 그 이유가 되는 사실 하나를 한 문장으로 쓴다(예: "이 호출은 이미 죽은 캐시 항목만 지우고 다른 일은 하지 않는다"). 이 사실이 참이면 위험 목록 대부분이 한꺼번에 해소된다. 6단계에서 실제 코드로 돌려 증명하고, 못 하면 "미증명(사다리 n)" 으로 적는다(규칙 14). 긴 "혹시" 목록을 쓰는 대신 이 사실에 시간을 쓴다.
6. **grep 이 멈추는 곳**을 본다 — 호출하는 라이브러리의 소스와 고정 버전·로컬 패치, 실행 시점(마이크로태스크·언마운트·정리 순서), API 가 돌려주는 JSON·DB 컬럼·와이어 포맷·같은 바이트를 읽는 다른 언어, 피처 플래그, 세 홉 아래 소비자. 심볼 검색이 못 찾는 소비자가 있으면 지도에 더한다. 확인하고 문제없던 위험은 버리지 않고 `prN-map.md` 의 「확인하고 해소한 위험」에 확인 방법·사다리 단계와 함께 적는다 — 8절 검증 표로 옮긴다.
7. 지도에 없는 경로를 전제로 한 주장·제안은 뒤 단계에서 적을 수 없다. 필요하면 지도를 먼저 넓힌다.

### 5. 축별 점검 — PR head worktree 의 `<sub>/`

```bash
cd "$S/prN-wt/<sub>"
```

4단계 지도의 갈라지는 지점부터 본다. 아래 `rg` 의 검색 경로 `<src>` 는 그 서브트리의 소스 디렉터리다. 범위 필터·계약이 구현된 자리는 프로필의 「횡단 보장」에서 읽는다.

**크리티컬 후보**

- 새 입력 경로가 기존 범위 필터(조직·권한·테넌트·검색 범위)를 지나는가. 기존 경로가 범위 값을 읽는 자리를 `rg -n "<범위 필드 이름>" <src>` 로 찾고, 새 경로가 같은 값을 읽는지 대조한다.
- 상태 플래그가 새로 켜지면 그 플래그를 읽는 코드를 `rg -n "<flag>" <src>` 로 전부 찾는다. 거부 목록·면제 목록을 본다.
- 새 어댑터의 예외 처리 절을 같은 계층의 기존 어댑터와 비교한다.
- 상수(`*_LIMIT`, `*_STREAK`, `*_BUDGET` 같은 한도·횟수)가 지시문·docstring 의 숫자와 "once"·"all" 같은 말과 맞는지 본다.

**중복 코드**

- 새 함수 본문의 특징 리터럴(딕셔너리 키, 에러 문구, 상수)로 `rg -n -F "<literal>" <src>` 를 돌려 같은 계층을 찾는다.
- 의심 쌍은 `python3 "$SK/scripts/dupcheck.py" --file <path>:<start>-<end> --file <path>:<start>-<end>` 로 잰다. 출력(ratio · 최장 공통 구간 · 구간 라벨)을 그대로 보고서에 적는다. `--html` 을 주면 9단계 `.compare` 블록이 나온다(`<mark>` 포함). 실행 기록은 `$S/prN-dup.log` 에 `tee -a` 로 모은다.

**기존 함수 미재사용**

- 새 헬퍼마다 이름·시그니처·docstring 키워드로 기존 모듈을 찾는다. 첫 후보는 프로필의 「재사용 후보 자리」다. 규칙 문서가 공통 코드를 찾는 순서를 정해 두었으면 그 순서를 따른다.
- UI 코드는 디자인 시스템과 같은 역할의 컴포넌트, 토큰이 아닌 색·hex, 두 곳 이상에 복사된 판단·상수를 미재사용·중복 축에 올린다.
- private 이름의 모듈 밖 사용을 찾는다. Python 이면 `rg -n "^from \.\w+ import .*\b_[a-z]" <src>`, 다른 언어는 그 언어의 비공개 표기(밑줄 접두사, `internal` 경로 등)로 찾는다.
- 재사용을 잘한 곳도 표로 적는다. 다음 리뷰에서 같은 의심을 되풀이하지 않기 위해서다.

**PR 테스트 점검** (pstack `principle-test-behavior-not-implementation`)

PR 이 추가·수정한 테스트마다 가상 편집 두 가지를 적용한다. 테스트는 사용자가 관찰할 수 있는 것(반환값·에러 타입·읽어 낼 수 있는 상태·밖으로 나간 요청)에 대한 주장이어야 한다.

- **동작을 깨뜨린다.** 테스트가 지키는 동작을 일부러 틀리게 한다 — 반환값 바꾸기, 효과 빼기, 효과 두 번. 그래도 통과하면 그 테스트는 아무것도 증명하지 않는다. 흔한 원인은 계약보다 느슨한 단정, 코드가 계산한 기대값, 코드를 거치지 않는 상수·프롬프트 문자열 복제, 테스트가 스스로 만든 데이터에 대한 단정이다. 이것은 실제로 돌린다 — 변경을 PR head worktree 에 임시로 넣고 그 테스트만 돌린 뒤 `git -C "$S/prN-wt" checkout -- <파일>` 로 바로 되돌린다(규칙 3 의 예외는 이 임시 변경뿐이고 `$W` 에서는 하지 않는다). 로그는 `$S/prN-mutation-<label>.log`. 통과한 로그가 증거다(chip `변이 실행`).
- **내부만 바꾼다.** 관찰 가능한 결과는 그대로 두고 구조를 바꾼다. 그때 실패하면 구현(내부 헬퍼 호출·호출 순서·중간 데이터)에 묶인 테스트다. 이것은 코드 대조로 적는다(단정이 가리키는 것이 계약인지 내부인지).

결과는 마이너로 올린다. 그 테스트가 크리티컬·메이저 계약의 유일한 보호막이면 메이저다. PR 의 테스트를 고치지 않는다(규칙 3). 제안은 "기대값을 요구사항에서 끌어낸다", "사용자 인터페이스로 구동한다" 처럼 바뀔 단정을 가리킨다.

**아키텍처 계약**

```bash
<프로필의 계약 검사 명령>                                         # <sub>/ 에서. 예: uv run lint-imports, pnpm depcruise
<프로필의 가드 테스트 명령>                                       # 규칙을 테스트로 지키는 레포면 그 테스트
git -C "$S/prN-wt" diff "$B"...HEAD -- <계약 설정 파일>           # 레포 루트 기준 경로. 계약 파일을 건드렸는가
```

- 규칙 원문: 4단계에서 읽은 서브트리 규칙 문서와 프로필의 「규칙 원문」 목록(아키텍처 문서, 계약 설정 파일의 머리 주석, 규칙 문서가 가리키는 `docs/`). 축마다 어느 문서의 어느 절을 근거로 삼는지 지도에 적어 둔다.
- 계약 검사 명령이 없는 서브트리는 lint·type-check 결과(8단계)와 문서 규칙을 계약 검사로 쓴다.
- 기계 검사가 못 보는 것:
  - 새 포트·어댑터가 규칙 원문이 정한 소유권 분류에 맞는 파일에 있는가.
  - 도메인을 모르도록 정한 계층(프레임워크·공용 모듈)에 도메인·도구 어휘가 이름으로 들어갔는가. `rg -c -i "<domain word>" <그 계층의 경로>`.
  - 미들웨어·플러그인이 정해진 주입 자리로 들어가는가. 등록 순서가 바뀌었는가.
  - 계약 설정에 예외(ignore) 줄을 더했는가. 더했으면 그 자체가 지적 대상이다("포트로 역전할 것").
  - 옛 API·필드·호환 shim 이 남았는가 — 새 함수가 생겼는데 옛 함수가 남음, 설정만 되고 읽히지 않는 필드, 두 이름이 같은 일을 함. `git -C "$S/prN-wt" diff "$B"...HEAD --stat` 으로 새 이름을 찾고 `rg` 로 옛 이름의 호출자를 센다. 호출자가 0 이거나 새 코드만 쓰면 지적한다 — 호환 계층을 남기지 않고 같은 변경에서 호출자를 옮기고 옛것을 지운다(pstack `migrate-callers-then-delete-legacy-apis`).
  - 경계 규율 — 검증·타입 좁히기·에러 처리가 경계(어댑터·설정 파싱·외부 API)에 있는가, 아니면 내부에서 다시 검증하는가. 내부 재검증, 경계 밖으로 새는 전송·저장 타입(wire 타입 re-export), 프레임워크 안에 묻힌 비즈니스 로직은 지적한다(pstack `boundary-discipline`). 질문은 "이 데이터가 지금 경계를 넘는가" 와 "순수 함수로 빼서 셸이 부르게 할 수 있는가" 두 개다.
  - 독자 부담 — 질문에서 답까지 거치는 계층 수와 독자가 머리에 들고 있어야 할 숨은·가변 상태를 센다. 호출자 하나뿐인 래퍼, 같은 메서드·인자를 그대로 넘기는 pass-through 계층, 구현체가 하나뿐인 어댑터, 동기화로 유지하는 파생 상태는 지적 후보다(pstack `minimize-reader-load`). 판정 질문은 "새 독자가 'X 는 어디서 오는가'·'무엇이 X 를 바꾸는가' 에 30초 안에 답할 수 있는가" 다. 7단계 구조 진단의 어휘로도 쓴다.

### 6. 재현 테스트 — PR head worktree 의 `<sub>/`

- 파일: 여러 개여도 된다(단위·조립·UI 가 다르면 파일을 나눈다). 자리는 그 서브트리의 기존 테스트 디렉터리이고, 이름에는 `zz_prN_review_repro` 를 넣는다 — Python 은 `test_zz_prN_review_repro[_<label>].py`, JS·TS 는 `zz_prN_review_repro[_<label>].test.ts(x)`, 다른 러너는 그 러너가 수집하는 이름 규칙에 이 문자열을 넣는다. fixture·Fake·테스트 헬퍼는 프로필의 「재현 테스트」에 적힌 것을 쓰고, 새로 만들지 않는다. 브라우저나 실 서버가 있어야 보이는 후보는 재현하지 않고 관찰로 내린다.
- 어댑터는 입력을 준비하는 순수 함수를 직접 부른다. 외부 시스템(DB·검색 클러스터·외부 API)은 작은 Fake 클래스로 대신한다.
- 테스트 하나 = 보고서 주장 하나. **단정은 결함 동작 자체를 검사한다**(거부 문구, 필터 부재, 잘못된 값). 결함이 없는 코드에서는 실패해야 한다. 통과 = 재현. 관측값을 출력으로 남긴다.
- 실행: `<프로필의 재현 테스트 러너> <file> 2>&1 | tee "$S/prN-repro-<label>.log"`. 예: `uv run pytest <file> -s -q -p no:cacheprovider`, `pnpm vitest run <file>`. 로그는 테스트 파일마다 하나다(`<label>` 은 파일 이름의 것과 같다). 덮어쓰지 않는다. 규칙 13 — 출력 요약 훅이 있는 환경이면 `rtk proxy <러너> …` 처럼 원문을 받는다. 8단계 suite 로그도 같다. 저장한 로그의 첫 줄이 요약 한 줄이면 다시 돌린다.
- 실패한 후보는 주장을 고치거나 관찰로 내린다. Fake 로 재현할 수 없는 후보(실 클러스터·마이그레이션)는 관찰로 내린다. 실 환경 재현은 하지 않는다.
- 4단계의 **안전 사실**도 재현 대상이다. 그 사실이 거짓이면 실패하는 작은 스크립트나 테스트를 써서 실제 코드(앱이 쓰는 같은 라이브러리·같은 함수)로 돌린다(사다리 4). 로그는 `$S/prN-safety.log`. 돌리지 못했으면 "미증명(사다리 n)" 과 어디서 멈췄는지를 적는다. 안전 사실이 거짓으로 드러나면 크리티컬·메이저 후보로 올려 보통 재현 절차를 밟는다.

### 7. 구조 판정

재현이 끝난 뒤, **4단계 지도 위에서** 결함 목록을 보고 묻는다. 지도가 없거나 결함이 지도 밖 경로에 있으면 먼저 4단계로 돌아간다.

1. **묶기** — "같은 코드 자리를 고치면 같이 사라지는 것"끼리 묶는다. 2건 이상이면 구조 후보다.
2. **결정 찾기** — 그 묶음을 만든 설계 결정을 한 문장으로 적는다. 흔한 모양:
   - 횡단 보장(범위·권한·증거 정책·예산)이 경계가 아니라 호출부마다 구현돼 있고, 새 경로가 그 호출부를 지나지 않는다.
   - 프레임워크 상태·플래그를 원래 뜻과 다른 뜻으로 재사용했다(상태 하나에 뜻 둘).
   - 공유해야 할 조립 로직이 한 클래스 안에 묶여 공개 함수가 없어 복사를 강요한다.
   - 병렬 arm·분기를 만들며 기존 arm 의 불변식을 옮기지 않았다.
   - 포트가 호출자의 값을 받기만 하고 강제하지 않는다.
3. **증거 셋** — (a) 그 결정으로 설명되는 확인된 결함 2건 이상(재현 또는 코드 대조) (b) 결정이 위반한 규칙 원문 (c) 레포에 이미 있는 대안 자리(파일:줄). 셋이 다 있어야 원인이다. 1건이면 원인이 아니라 그 항목의 제안이다.
4. **두 길** — 근본 수정: 무엇을 어디로 옮기는지, 바뀌는 시그니처·파일 수, PR 범위 안인지 밖인지, 어떤 기존 테스트가 지켜 주는지. **4단계 지도의 구간·단위를 그대로 인용한다** — 제안이 바꾸는 이벤트·저장·전파·소비 지점을 파일:줄로 적고, 제안이 실제로 그 비용·결함을 없애는지 말로 검증한다(예: 전파가 스냅샷 단위면 델타 이벤트는 전파량을 줄이지 않는다). 증상 패치: 이 PR 안에서 결함만 없애는 길과 그 대가. 증상 패치가 틀린 방향이면 "권하지 않음"과 이유를 적는다.
5. **판정 반영** — 원인이 하나라도 있으면 보고서 1절이 구조 진단이고 요약 리뷰에도 구조 단락이 들어간다(10단계 순서). 근본 수정이 PR 범위를 넘으면 "후속 Story + 이 PR 은 증상 패치" 선택지를 주고, 어느 쪽인지 PR 본문에 적어 달라고 요청한다. 증상 패치를 권하지 않는 원인이 있으면 판정은 "구조 재검토 필요"다.
6. 원인 밖의 결함은 국소 결함으로 표시한다.

### 결정 기록 — 제안을 정하는 순간(5·6·7단계)

제안 한 줄이 나올 때마다 `$S/prN-decisions.md` 에 항목 chip(`M5`, `원인 A` 같은 ID) 아래 다음 6항을 적는다. 9단계에서 기억으로 재구성하지 않는다 — 지도를 먼저 그리는 것과 같은 이유다. 6항 중 하나라도 비면 그 제안은 적지 않고 결함만 적는다(규칙 11).

| 항 | 적는 것 |
|---|---|
| 구간 | 결함이 4단계 지도의 어느 구간에서 오는가. 파일:줄 |
| 대안 | 한 줄에 하나. 첫 줄은 「채택」 + 고른 길 + 이유 한 문장, 다음 줄부터 「기각」 + 저울질한 다른 길 + 기각 이유 한 문장. "고치지 않고 관찰로 내림"도 대안이다. 길이 하나뿐이었으면 「기각」 줄 대신 왜 하나뿐인지 한 줄(예: 같은 계층에 다른 자리가 없다) |
| 근거 | 제안이 지키는 규칙 원문 또는 레포에 이미 있는 선례. 파일:줄 |
| 적합성 | 규칙 11 의 (a)(b)(c) 를 한 줄씩, 세 줄. (a) 존재: 돌린 `rg` 명령과 결과 (b) 계층: 그 계층·단위에서 그 값을 읽어도 되는가 (c) 해소: 결함이 없어지는 이유. 한 줄은 두 문장을 넘기지 않는다 |
| 비용 | 바뀌는 파일 수·시그니처. PR 범위 안인지 밖인지 |
| 강제 수준 | 제안이 지켜지는 수준을 하나 고른다 — 아키텍처(상태의 소유자 하나·방법 하나, 잘못된 import 가 실패) > 타입(나쁜 상태를 쓸 수 없음) > lint·CI 검사(오류 문구가 고칠 파일·함수를 말함) > 테스트 > 문서·에이전트 규칙. 고른 수준과, 더 높은 수준이 왜 안 되는지 한 줄. 문서 수준이면 "어겨도 아무것도 실패하지 않는다" 를 적는다(pstack `correct`). 같은 실수가 이 레포에서 두 번째면 그 사실도 적는다 — 반복은 더 높은 수준으로 올릴 근거다 |

구조 진단(7단계)의 근본 수정과 증상 패치는 각각 한 기록이다. 7단계 4항 "두 길"의 내용을 이 6항으로 적는다.

### 8. 기계 검증 — PR head worktree 의 `<sub>/`

프로필의 「기계 검증」 명령을 그대로 돌린다. CI 가 그 서브트리에 돌리는 lint·format·type-check·test 와 같은 명령이어야 한다.

```bash
<lint 명령> ; <format 검사 명령>                                   # 재현 테스트 파일(*zz_prN_review_repro*)은 범위에서 뺀다
<test 명령> <suite> 2>&1 | tee "$S/prN-suite-<sub>.log"            # suite = diff 에 든 테스트 디렉터리 + 변경 모듈을 덮는 테스트 디렉터리
```

재현 테스트 파일은 리뷰어의 것이므로 lint·format 범위에서 뺀다(예: `ruff check --exclude '*review_repro*'`). 로그는 규칙 13 대로 원문이다. `<sub>` 가 `.` 이면 로그 이름은 `prN-suite-root.log` 로 쓴다.
**실패가 있으면 base 에서 같은 테스트만 다시 돌린다.** 1단계 `gh pr checks` 의 실패도 같은 방법으로 가른다.

```bash
S="${PR_REVIEW_DIR:-$HOME/.pr-reviews}/prN"; BASE=<1단계 baseRefName>
[ -d "$S/prN-base" ] || git worktree add "$S/prN-base" "origin/$BASE" --detach
(cd "$S/prN-base/<sub>" && <같은 러너> <실패한 테스트 id 들>) 2>&1 | tee "$S/prN-base-fail.log"
```

- base 에서도 실패 → chip `기존 실패`. 판정 수에 세지 않고 8절 검증 표에 "기존 실패 n건(base 동일)" 로 적는다. 이 PR 의 결함으로 적지 않는다.
- base 에서 통과 → PR 결함 후보다. 6단계로 돌아가 재현 테스트로 고정한다. 코드가 아니라 테스트 쪽이 바뀐 것이면 그 사실을 적는다.
- base worktree 에도 프로필의 「의존성 준비」를 적용한다.

### 9. HTML 보고서 — PR 마다 Artifact 하나

보고서 모양은 이 스킬 폴더의 템플릿이 정한다. `cp "$SK/report-template.html" "$S/prN-review.html"` 로 복사한 뒤 채운다. Artifact 가 있는 환경과 없는 환경이 같은 파일을 만들고, 다른 점은 발행 URL 유무뿐이다. 템플릿의 CSS·절 순서·항목 행·`details.why` 상자를 바꾸지 않고, 템플릿 안의 HTML 주석(`<!-- -->`)은 채운 뒤 지운다. 그림은 1절 `<figure>` 의 인라인 SVG 자리에 "지금 / 제안" 두 줄 흐름을 그린다. 제목은 `PR #NNNN <주제> 리뷰`. 구조는 고정이다.

1. 판정 상자 — 판정 한 줄, 중복·미재사용 요약, 아키텍처 요약, 구조 요약(원인 수, 근본 수정이 PR 범위를 넘는지), 검증 방식("문제는 전부 재현 테스트로 확인"), 안전 사실 한 줄(증명됨 n/5 또는 미증명).
2. 카운트 타일 — 구조 원인 · 크리티컬 · 메이저 · 중복·미재사용 · 아키텍처 · 기타 마이너 · 재현 테스트 N/N · 기존 테스트.
3. 절: 1 구조 진단(원인마다 증거 · 그림 · 근본 수정 | 증상 패치 두 칸) → 2 크리티컬·메이저 → 3 중복·미재사용 → 4 아키텍처 계약(표 + 발견) → 5 기타 마이너 → 6 관찰(판정 수 제외) → 7 재사용을 잘한 곳 → 8 검증(기계 검증 표 · 재현 테스트 파일별 로그 · 기존 실패 · 안전 사실과 사다리 단계 · 확인하고 해소한 위험 표(사다리 4 이상만) · PR 테스트 변이 실행 결과 · 후보 처리표 · 재리뷰면 이전 항목 상태표). 원인이 0개면 1절은 "구조 진단 — 원인 없음. 결함은 전부 국소다" 한 줄이다.
4. 항목마다: 심각도 또는 축 chip + 확인 방법 chip + where(파일:줄) + 재현 note(테스트 이름 + 관측값) + 제안 1개(규칙 11 로 확인한 것만) + 제안 근거 상자(템플릿의 `details.why`). 안에는 그 항목의 결정 기록 6항을 `prN-decisions.md` 에서 옮겨 적는다. 1절의 근본 수정·증상 패치 칸에도 같은 상자를 둔다. 제안이 없는 항목에는 상자도 없다. 중복 항목의 증거는 코드 조각이 여러 줄이면 템플릿의 `.compare` 블록(`dupcheck.py --html` 출력을 그대로 붙인다 — 조각마다 `figure`+`pre`, 캡션에 파일:줄, 최장 공통 구간 `<mark>`)으로, 한 줄짜리 조각들은 `pre` 하나에 줄마다 주석으로 적는다. 두 조각을 공백으로 맞춘 2단 `pre` 는 쓰지 않는다.
5. **발행 전 기계 점검** — `python3 "$SK/scripts/check-report.py" "$S/prN-review.html"`. 남은 템플릿 주석·자리표시자가 있으면 실패다. 이어서 나오는 추측 표현 후보 목록은 문장마다 읽는다. 결과 주장이면 확인한 사실로 바꾸거나 지운다. 기능 설명("테스트에서 시계를 바꿔 끼울 수 있다")은 남겨도 된다. 통과할 때까지 반복한다.

**Artifact 없는 환경 — 발행하지 않는다.** `open "$S/prN-review.html"` 로 브라우저에 연다. `prN-artifact-url.txt` 는 만들지 않는다. URL 을 지어내지 않는다. 10단계의 링크 박스와 링크 전용 코멘트를 생략하고 9단계는 끝난다.

**발행 — Artifact 가 있는 환경, 세션 디렉터리.** Artifact 도구는 세션 디렉터리 또는 scratchpad 아래 파일만 받는다. `$S` 는 밖이므로 git 제외 폴더로 복사한다.

```bash
W=$(git rev-parse --show-toplevel); S="${PR_REVIEW_DIR:-$HOME/.pr-reviews}/prN"
mkdir -p "$W/.review"
grep -qx ".review/" "$(git rev-parse --git-path info/exclude)" || echo ".review/" >> "$(git rev-parse --git-path info/exclude)"
cp "$S/prN-review.html" "$W/.review/prN-review.html"
```

- 첫 발행: `Artifact(file_path="$W/.review/prN-review.html", icon="clipboard", description="…")`. URL 을 `$S/prN-artifact-url.txt` 에 적어 둔다.
- 재발행(같은 세션): 같은 `file_path` 로 다시 발행한다. 재발행(새 세션·재리뷰): `url=` 에 저장해 둔 URL 을 넘긴다. 새 아티팩트를 만들지 않는다.
- **첫 발행 직후** 사용자에게 묻는다: "Share 메뉴에서 「링크가 있는 모든 사용자」(Anyone with the link)로 설정했나요?" 기본은 발행자만이고 도구로는 바꿀 수도 확인할 수도 없다. "예"를 받기 전에는 게시하지 않는다. 같은 URL 재발행은 공유 설정이 유지되므로 다시 묻지 않는다.

왜 Artifact 인가: GitHub 코멘트는 `.html` 첨부를 받지 않고 `gh` 에 첨부 API 가 없다. gist·Pages 는 레포 밖에 파일을 하나 더 관리해야 하고, 같은 URL 재발행은 Artifact 도구가 직접 한다. Markdown 은 보고서 모양을 살리지 못한다.

### 10. 코멘트 초안

파일 세 개를 만든다. 게시하지 않는다. Artifact 없는 환경이면 `prN-link-comment.md` 는 만들지 않고 두 개다. 본문 형식(인라인 3항 · 요약 리뷰 8항 순서 · 링크 전용 코멘트)은 `$SK/reference/publish.md` 에 있다 — 초안을 쓰기 전에 읽는다.

- `$S/prN-review.json` — `gh api` 입력. `{"commit_id": "<head sha>", "event": "COMMENT", "body": "<요약 리뷰 본문>", "comments": [{"path", "line", "side": "RIGHT", "body"}]}`. `comments` 에는 **크리티컬·메이저만** 넣는다. 없으면 빈 배열이다. 재리뷰면 요약 본문은 `$S/prN-review-body.json`(`{"body": "…"}`, PUT 입력)에 따로 두고, `prN-review.json` 에는 새 인라인만 둔다.
- `$S/prN-link-comment.md` — 마지막 코멘트, 보고서 링크 전용. Artifact 가 있는 환경에서만 만든다.
- `$S/prN-comments.md` — 사람이 읽는 초안. 위 둘의 내용을 한 파일에 모은다.

**인라인 코멘트** — 크리티컬·메이저에만 단다. 마이너·중복·미재사용·아키텍처·관찰은 인라인으로 달지 않는다 — 요약 표에 한 줄씩 적고 자세한 것은 보고서 링크로 보낸다. 구조 문제는 인라인이 아니라 요약 본문에 둔다.

**기계 점검 — 둘 다 통과해야 초안이다.**

```bash
SK=<이 스킬의 base 디렉터리>; S="${PR_REVIEW_DIR:-$HOME/.pr-reviews}/prN"
python3 "$SK/scripts/check-report.py" "$S/prN-comments.md" "$S/prN-review.json" "$S/prN-link-comment.md" "$S/prN-decisions.md"   # 추측 표현. 결과 주장이 하나라도 남으면 게시하지 않는다
gh pr diff N | python3 "$SK/scripts/check-inline-lines.py" "$S/prN-review.json"                                          # line·start_line 이 hunk 밖이면 리뷰 POST 전체가 422
```

**게시 — 승인 뒤 별도 턴.** 명령·순서·`prN-published.json` 기록·재리뷰 갱신(PUT·DELETE·PATCH)은 `$SK/reference/publish.md` 를 읽고 그대로 따른다.

### 11. 정리 — 게시 턴이 끝난 뒤

```bash
S="${PR_REVIEW_DIR:-$HOME/.pr-reviews}/prN"
find "$S/prN-wt" -name '*zz_prN_review_repro*' | grep -v node_modules | xargs -I{} cp {} "$S/"   # 재현 파일 전부. 복사된 수를 ls 로 확인한 뒤에 worktree 를 지운다 — 출력 요약 훅(rtk)은 -not·-exec 가 든 find 를 거부한다
```

## 레포 프로필

이 스킬의 절차는 레포와 무관하다. 레포마다 다른 값은 프로필 한 곳에 모은다. 프로필은 변경 파일이 속한 서브트리마다 한 묶음이다.

1. `$W/.claude/review-pr.md` 가 있으면 그것이 프로필이다. 레포 관리자가 유지하는 파일이다.
2. 없으면 1단계에서 아래 표의 「찾는 곳」을 조사해 `$S/prN-profile.md` 에 쓴다. 찾지 못한 항목은 "없음" 으로 적고, 그 항목에 의존하는 점검은 건너뛴 사실을 8절 검증 표에 적는다. 명령을 지어내지 않는다.
3. 조사한 프로필을 레포에 저장하지 않는다(규칙 3). 저장을 권할 때는 채팅 답변 끝에 한 줄로 알린다.

| 항목 | 뜻 | 프로필 파일이 없을 때 찾는 곳 |
|---|---|---|
| 서브트리 | 변경 파일이 속한 패키지 디렉터리 | 매니페스트(`pyproject.toml`·`package.json`·`go.mod`·`Cargo.toml` 등)가 있는 가장 가까운 상위 디렉터리 |
| 규칙 원문 | 아키텍처·컨벤션 문서와 절 | `<sub>/CLAUDE.md`·`AGENTS.md`·`ARCHITECTURE.md`·`CONTRIBUTING.md`, 루트의 같은 문서, 그 문서가 가리키는 `docs/` |
| 계약 검사 | import 계약·경계를 기계로 검사하는 명령과 설정 파일 | `.importlinter`, dependency-cruiser·eslint boundaries 설정, 아키텍처 가드 테스트 |
| 횡단 보장 | 범위·권한·테넌시 필터가 구현된 자리 | 규칙 원문, 기존 경로가 범위 값을 읽는 코드 |
| 재사용 후보 자리 | 공통 헬퍼·공용 컴포넌트를 두는 모듈 | 규칙 원문의 구조 절, `shared`·`common`·`lib`·`utils`·디자인 시스템 패키지 |
| 재현 테스트 | 러너 명령, 파일 자리, 쓸 fixture·Fake·테스트 헬퍼 | 같은 서브트리의 기존 테스트, `conftest.py`·test utils, 테스트 문서 |
| 기계 검증 | lint·format·type-check·test 명령 | 그 서브트리를 잡는 CI 워크플로(`.github/workflows/`), pre-commit 설정, 매니페스트의 scripts |
| 의존성 준비 | worktree 에서 테스트를 돌리기 위한 준비 | 패키지 관리자와 lockfile. 아래 절차 |

**의존성 준비** — worktree 에는 설치된 의존성이 없다. 가상 환경을 스스로 만드는 러너(`uv run` 등)는 준비가 필요 없다. `node_modules` 를 쓰는 서브트리는 lockfile 이 세션 체크아웃과 worktree 에서 같으면(`cmp "$W/<lockfile>" "$S/prN-wt/<lockfile>"`) `ln -s "$W/<dir>/node_modules" "$S/prN-wt/<dir>/node_modules"` 로 연결한다. 워크스페이스 레포면 루트와 패키지 두 곳을 연결한다. lockfile 이 다르면 worktree 에서 lockfile 을 고정한 설치 명령(`pnpm install --frozen-lockfile`, `npm ci`)을 돌린다.

**UI 서브트리의 아키텍처 축**

- 디자인 시스템 패키지를 건드리면 그 패키지의 규칙 문서도 규칙 원문이다.
- 목 드리프트: API 스키마(GraphQL·OpenAPI)에서 필드·타입·enum 이 바뀌었는데 테스트·스토리가 쓰는 목이 같은 변경에 없으면 지적한다.
- TS 규칙 표: pstack `typescript-best-practices`(`$HOME/.claude/plugins/cache/cursor-plugins/pstack/*/skills/typescript-best-practices/SKILL.md`, 예시는 같은 폴더 `references/patterns.md`). 보는 것은 `as` 캐스트, 판별 유니온, `never` 소진 검사, `unknown`, 스키마 파생 타입, `satisfies`. 위반은 마이너다. pstack 이 없으면 이 항목은 생략한다.

5·6·8단계 머리의 `<sub>/` 는 서브트리마다 그 디렉터리로 바꾼다. 로그 이름의 `<sub>`·`<label>` 로 서브트리와 파일을 구분한다.

## 멈춰서 묻는 지점

1. 1단계 뒤 — 변경이 두 서브트리에 걸치거나 `baseRefName` 이 기본 브랜치가 아니면, 비교 기준과 검증 범위를 확인한다. 프로필에서 「기계 검증」 명령을 찾지 못했으면 쓸 명령을 묻는다.
2. 9단계 뒤 — 첫 발행이면 Artifact URL 을 주고 공개 범위(링크가 있는 모든 사용자) 설정 여부를 묻는다. 같은 URL 재발행이면 URL 만 주고 묻지 않는다. Artifact 없는 환경이면 로컬 파일 경로를 주고 묻지 않는다.
3. 10단계 뒤 — 초안 세 파일 경로와 채팅 요약을 보여 주고 게시 승인을 묻는다.
4. 게시 턴 — HEAD 가 payload 와 다르면 중단하고 재리뷰 여부를 묻는다.

## 채팅 답변 형식

1. 판정 한 줄.
2. 구조 진단 — 원인 수와 각 원인 한 줄. 근본 수정이 PR 범위를 넘는지.
3. 크리티컬·메이저 — 항목마다 재현 결과 한 줄.
4. 중복·미재사용 — 항목 나열.
5. 아키텍처 — 계약 결과 한 줄 + 발견.
6. 검증 한 줄 또는 표. 안전 사실 한 줄(증명 여부·사다리 단계).
7. 보고서 URL(Artifact 없는 환경이면 로컬 파일 경로) + 공개 범위 설정 질문(첫 발행 때만) + 초안 파일의 실제 경로 + "게시는 승인 뒤". 재리뷰면 이전 항목 상태 한 줄(해소 a · 잔존 b · 결정으로 내림 c)을 2번 앞에 둔다.

## 하지 않는 것

- 코드 수정, 레포 커밋, 기본 브랜치 푸시, 승인 전 게시, 승인 전 worktree 삭제.
- 마이너·중복·미재사용·아키텍처·관찰 항목에 인라인 코멘트 달기.
- 재현하지 않은 "문제" 보고. 증거 셋 없는 "구조적으로 틀렸다" 주장. 바뀌는 경로를 코드로 확인하지 않은 근본 수정 제안. 존재·적합성을 확인하지 않은 제안. 결정 기록 없는 제안. "~수 있다"·"~예상된다" 로 끝나는 결과 주장.
- 리뷰 봇·백그라운드 리뷰어·interrogate 결과를 확인 없이 옮겨 적기. 기각한 후보를 후보 처리표 없이 버리기. 프로필에 없는 명령을 지어내기.
- 손으로 쓴 `SequenceMatcher` 호출. 요약 훅을 거친 로그 저장. 이전 산출물을 읽지 않은 재리뷰. base 대조 없이 실패 테스트를 PR 결함으로 적기. `prN-published.json` 을 남기지 않은 게시.
- gist·Pages·Notion 링크, Markdown 전체 보고서 코멘트, 브라우저 자동화 첨부, 특정 사용자 경로.
- 사다리 3 이하의 사실을 「확인하고 해소한 위험」에 적기. 변이 실행 뒤 worktree 되돌리기 생략. 적대자 worktree 남기기. PR 의 테스트를 고치기.
