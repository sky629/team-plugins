# run_final_check

구현과 검증이 끝난 작업 브랜치를 팀에 내놓는 절차입니다. 팀원에게 알림이 가는 행동은 전부 마지막 승인 뒤로 미룹니다. 사용자가 멈추는 곳은 한 번입니다.

```
드래프트 PR(알림 없음) → 자기 리뷰 → 수정 → 보고서 발행(비공개)
  → ★ 멈춤 → 코멘트 게시 · 리뷰어 지정 · Ready for review
```

## 이 스킬이 허용하는 것과 허용하지 않는 것

사용자가 `/run_final_check` 를 부르거나 이 파일을 따르라고 지시한 것은 **작업 브랜치 푸시와 드래프트 PR 생성**에 대한 승인입니다. 그 밖의 외부 쓰기는 6단계의 승인 뒤에만 합니다.

| 행동 | 승인 전 | 승인 뒤 |
|---|---|---|
| 작업 브랜치 푸시 | 한다 | 한다 |
| 드래프트 PR 생성(리뷰어 없음, 멘션 없음) | 한다 | |
| 보고서 발행(비공개) | 한다 | |
| PR 코멘트·리뷰 게시 | 하지 않는다 | 한다 |
| 리뷰어 지정, 본문의 `@` 멘션 | 하지 않는다 | 한다 |
| Ready for review 전환 | 하지 않는다 | 한다 |
| 공용 브랜치(main, develop, 환경 브랜치) 푸시·머지 | 하지 않는다 | 하지 않는다 |

## 1. 전제 확인

하나라도 어긋나면 멈추고 보고합니다.

- 현재 브랜치가 작업 브랜치입니다. 공용 브랜치가 아닙니다.
- 작업 트리에 커밋하지 않은 변경이 없습니다.
- 프로젝트의 CI 와 같은 검사(포맷, 린트, 타입, 전체 테스트)가 통과합니다. 기존 실패가 있으면 부모 커밋에서도 실패하는지 확인하고 구분해서 적습니다.
- 스펙이 있으면 완료 조건이 검증된 상태입니다.

## 2. 드래프트 PR: 프로젝트의 PR 스킬로 만든다

프로젝트에 PR 스킬이 있으면 그 스킬을 호출해서 PR 을 만듭니다. 본문을 직접 지어 쓰지 않습니다. PR 스킬의 분석과 작성 절차(base 브랜치 판별, 변경 분석, 계약 영향, 담당자 산출, 설계 결정과 근거, 템플릿의 모든 절, 제목 규칙, 라벨)는 그대로 따릅니다.

PR 스킬의 절차에서 다음 세 가지만 바꿉니다. 이 드래프트는 팀원에게 알림을 보내지 않고, 승인은 6단계에서 한 번에 받기 때문입니다.

| PR 스킬의 절차 | 이 스킬에서 |
|---|---|
| 본문 초안을 보여 주고 승인을 받은 뒤 푸시·생성한다 | 승인을 기다리지 않고 푸시해서 **드래프트**로 만든다(`gh pr create --draft`). 초안 내용의 승인은 6단계에서 받는다. |
| 만들 때 `--reviewer` 로 리뷰어를 지정한다 | 지정하지 않는다. 산출한 리뷰어 목록을 파일에 적어 두고 7단계에서 지정한다. |
| 본문에 담당자를 `@` 로 멘션한다 | `@` 없이 백틱으로 적는다(예: `` `org/team` ``). 7단계에서 멘션으로 바꾼다. |

base 브랜치는 PR 스킬이 판별한 기본값을 씁니다. 스펙에 기준 브랜치가 적혀 있으면 그것과 같은지 확인합니다. 6단계에서 사용자에게 보여 주고, 다르다고 하면 `gh pr edit --base` 로 바꿉니다.

프로젝트에 PR 스킬이 없으면 PR 템플릿을 따라 본문을 쓰고 같은 방식으로 드래프트를 만듭니다.

## 3. 자기 리뷰

리뷰는 이 세션이 직접 하지 않고 **새 서브에이전트 하나**에 맡깁니다. 이유는 두 가지입니다. 구현한 세션은 왜 그렇게 짰는지 알고 있어서 결함을 넘기기 쉽습니다. 그리고 구현을 끝낸 세션은 컨텍스트가 많이 차 있어서 리뷰까지 하면 앞 단계의 내용을 잃을 수 있습니다.

서브에이전트에는 다음만 넘깁니다. 대화 내용, 구현 중의 판단, 예상되는 결함은 넘기지 않습니다.

- PR 번호와 레포의 절대 경로
- 스펙 파일의 절대 경로(있을 때)
- 항목 파일을 쓸 절대 경로(리뷰 스킬의 산출물 폴더 안)
- 아래 지시

```
<레포 절대 경로> 의 PR #N 을 리뷰하십시오. 당신은 이 PR 을 구현하지 않았습니다.

1. 프로젝트의 PR 리뷰 스킬이 있으면 그 스킬을 호출해서 처음부터 코멘트 초안 작성까지 따르십시오. 없으면 code-review 스킬을 쓰십시오. 스킬이 정한 재현 절차는 생략하지 마십시오. 아래 세 가지만 스킬과 다르게 하십시오.
   - 보고서: HTML 보고서를 만들거나 발행하지 마십시오. 항목 목록을 <항목 파일 절대 경로> 에 Markdown 으로 쓰십시오. 항목마다 심각도, 파일:줄, 재현 파일 경로와 재현 명령, 재현 결과, 제안을 적으십시오.
   - 적대 검토: 다음 둘 중 하나에 해당할 때만 적대 검토자를 띄우고, 띄울 때는 1명만 띄우십시오. (가) 테스트와 생성 파일을 뺀 변경이 400줄 이상이다. (나) 후보 수집에서 사실이라면 크리티컬 또는 메이저인 후보가 나왔다. 둘 다 아니면 적대 검토를 건너뛰고 보고에 「적대 검토: 건너뜀(조건 미충족)」 이라고 적으십시오.
   - 명령 출력: 테스트, 린트, 타입 검사처럼 출력이 긴 명령은 출력을 파일로 보내고 끝 40줄만 읽으십시오. 실패했을 때만 필요한 부분을 더 읽으십시오.
2. 리뷰의 의도는 PR 본문과 <스펙 절대 경로> 를 함께 기준으로 삼으십시오. 스펙의 「결정한 것」 과 「완료 조건」 을 PR 이 지키는지 확인하십시오. PR 본문과 스펙이 어긋나면 결함으로 적으십시오.
3. GitHub 에 아무것도 게시하지 마십시오. 코드를 고치지 마십시오. 재현 파일은 리뷰 스킬이 정한 위치에만 두십시오.
4. 사용자에게 질문할 수 없습니다. 스킬이 사용자에게 묻는 단계(보고서 공개 범위, 게시 승인)는 건너뛰고, 물어야 했던 질문을 보고에 적으십시오.
5. 직접 띄운 서브에이전트나 백그라운드 작업이 있으면 전부 끝난 뒤에 보고하십시오. 끝나지 않았거나 실행하지 못한 단계가 있으면 어떤 단계인지 적으십시오.

보고할 것: 판정 한 줄, 항목 파일 경로, 결정 필요 항목, 코멘트 초안 파일 경로, 리뷰한 HEAD 커밋, 적대 검토 실행 여부와 이유, 건너뛴 단계.
```

서브에이전트의 보고는 그대로 믿지 않습니다. 다만 모든 항목의 재현을 다시 실행하지는 않습니다. 4단계에서 고치기로 한 항목만, 고치기 직전에 재현 명령을 직접 실행해서 실패를 확인합니다. 고치지 않고 남기는 항목은 항목 파일에 적힌 재현 결과를 씁니다. 서브에이전트가 재현을 실행하지 못했다고 보고하면 6단계에서 그 사실을 사용자에게 알립니다. 적대 검토를 건너뛰었으면 그 사실과 이유도 6단계에서 알립니다.

## 4. 수정

리뷰 결과를 셋으로 나눕니다.

| 종류 | 처리 |
|---|---|
| 재현한 결함이고, 잃는 것이 없는 수정이 있다 | 아래 심각도 기준에 따라 고칩니다. 재현 테스트가 통과하는지 확인하고 커밋·푸시합니다. |
| 결정이 필요하다(모든 선택지가 무언가를 잃는다) | 고치지 않습니다. 6단계에서 사용자에게 올립니다. |
| 근본 수정이 PR 범위를 넘는다 | 고치지 않습니다. 후속 작업 후보로 적습니다. |

고칠지는 심각도로 정합니다. 심각도는 리뷰 스킬이 매긴 것을 씁니다.

| 심각도 | 처리 |
|---|---|
| 크리티컬, 메이저 | 고칩니다. |
| 마이너 | 수정이 한 곳(함수 하나 또는 파일 하나의 인접한 줄)에 그치고 다른 동작을 바꾸지 않으면 고칩니다. 그렇지 않으면 남깁니다. |
| 중복, 미재사용, 아키텍처 지적 | 이 PR 이 새로 만든 것이고 수정이 이 PR 의 변경 안에서 끝나면 고칩니다. 기존 코드를 함께 옮겨야 하면 남깁니다. |
| 관찰 | 고치지 않습니다. |

남긴 항목은 이유와 함께 보고서의 「남은 항목」 에 적습니다. 마이너를 전부 고치려고 반복을 늘리지 않습니다.

수정은 이 세션이 합니다. 스펙과 승인된 구조 설계를 알고 있어야 그 안에서 고칠 수 있기 때문입니다. 수정한 뒤의 재리뷰는 **새 서브에이전트**에 맡깁니다. 첫 리뷰를 한 서브에이전트는 컨텍스트가 가득 차 있어서, 이어서 쓰면 턴마다 그 컨텍스트 전체를 다시 읽는 비용이 듭니다. 새 서브에이전트에는 다음만 넘깁니다.

- 레포의 절대 경로, PR 번호, 리뷰한 이전 HEAD 커밋과 새 HEAD 커밋
- 항목 파일의 절대 경로와, 그중 이번에 고친 항목의 번호
- 지시: 「이전 HEAD 와 새 HEAD 사이의 diff 만 리뷰하십시오. 고친 항목마다 재현 테스트가 통과하는지 확인하고, 이 diff 가 새 결함을 만들었는지 보십시오. PR 전체를 다시 리뷰하지 마십시오. 적대 검토자를 띄우지 마십시오. HTML 보고서를 만들지 마십시오. 결과를 항목 파일에 덧붙이고, 코멘트 초안을 남은 항목에 맞게 고치십시오. GitHub 에 게시하지 말고 코드를 고치지 마십시오. 출력이 긴 명령은 파일로 보내고 끝 40줄만 읽으십시오.」

수정은 한 번, 재리뷰도 한 번입니다. 재리뷰에서 결함이 나오면 더 고치지 않고 6단계로 갑니다. 그 결함은 이유와 함께 보고서의 「남은 항목」 에 적습니다. 수정한 자리에서 결함이 다시 나왔으면 구조 원인으로 올립니다.

재리뷰의 결과로 Ready 전환에 대한 권고를 정합니다.

| 재리뷰의 상태 | 권고 |
|---|---|
| 크리티컬·메이저가 없다 | Ready 전환을 권합니다. |
| 크리티컬·메이저가 남아 있다 | Ready 전환을 권하지 않습니다. 드래프트로 두고, 남은 결함과 수정이 무엇을 바꿨는지 보여 줍니다. |
| 결정 필요 항목이 남아 있다 | 결정에 묶인 결함이 크리티컬·메이저면 Ready 전환을 권하지 않습니다. 사용자가 결정하면 그에 따라 고치고 재리뷰를 한 번 더 합니다. 이 수정과 재리뷰는 한 번의 한도에 넣지 않습니다. |
| 재리뷰가 끝나지 않았거나 리뷰 단계 일부를 건너뛰었다 | Ready 전환을 권하지 않습니다. 무엇이 확인되지 않았는지 적습니다. 3단계의 조건에 따라 적대 검토를 건너뛴 것은 여기에 해당하지 않습니다. |

권고는 권고입니다. 전환할지는 사용자가 6단계에서 정합니다.

수정은 스펙의 결정과 승인된 구조 설계 안에서만 합니다. 벗어나야 하면 고치지 않고 올립니다. 수정으로 PR 본문의 내용이 달라지면 본문도 고칩니다.

## 5. 보고서

보고서는 이 단계에서 한 번만 만듭니다. 리뷰 서브에이전트는 보고서를 만들지 않으므로, 항목 파일과 4단계의 수정 결과를 재료로 삼아 리뷰 스킬의 형식으로 최종 보고서를 만들고 발행합니다. 발행은 비공개 상태로 둡니다. 보고서에는 다음이 구분되어 있어야 합니다.

- 리뷰에서 찾아 이미 고친 것(커밋 포함)
- 남은 항목
- 결정 필요 항목

코멘트 초안은 **남은 항목과 결정 필요 항목만** 담습니다. 이미 고친 결함을 코멘트로 게시하지 않습니다. 고친 것은 요약 한 단락으로만 적습니다.

## 6. 멈춤: 한 번에 승인받기

다음을 보여 주고 멈춥니다.

1. 드래프트 PR 의 URL, base 브랜치, 제목, 본문 전체
2. 「설계 결정과 근거」 항목마다 그 근거를 어디서 가져왔는지(대화, 스펙, 커밋, 이슈). 대화에만 보여 주고 본문에는 넣지 않습니다.
3. 리뷰 판정 한 줄, Ready 전환 권고(권함 또는 권하지 않음, 이유 한 줄), 적대 검토 실행 여부와 이유
4. 고친 것의 목록(결함, 심각도, 커밋)과 수정 횟수
5. 남은 항목(심각도, 남긴 이유)과 결정 필요 항목
6. 보고서 URL(또는 로컬 경로)과 코멘트 초안 파일 경로
7. 승인하면 실행할 행동의 목록: 게시할 코멘트 수, 지정할 리뷰어, 본문에 넣을 멘션, 붙일 라벨, Ready for review 전환
8. 보고서 공개 범위를 「링크가 있는 모든 사용자」 로 바꿨는지 묻는 질문(도구로는 바꿀 수 없습니다)

사용자는 일부만 승인할 수 있습니다. 예: 「Ready 전환과 리뷰어 지정만 하고 코멘트는 올리지 마」. 본문 수정 요청이 오면 고치고 다시 보여 줍니다.

## 7. 게시 (승인 뒤)

승인받은 항목만, 이 순서로 실행합니다.

1. PR 의 HEAD 가 리뷰한 커밋과 같은지 확인합니다. 다르면 멈추고 재리뷰 여부를 묻습니다.
2. 리뷰 스킬의 게시 절차로 코멘트를 게시합니다.
3. 본문의 담당자 표기를 `@` 멘션으로 바꿉니다(`gh pr edit --body-file`).
4. 리뷰어를 지정합니다(`gh pr edit --add-reviewer`). 거부된 리뷰어는 빼고 진행한 뒤 어떤 것이 빠졌는지 보고합니다.
5. `gh pr ready` 로 전환합니다. 권고가 「권하지 않음」 이었으면 사용자가 전환을 명시적으로 승인한 경우에만 합니다.
6. 게시한 것의 URL 과 id 를 보고합니다.

코멘트를 먼저 게시하고 Ready 전환을 마지막에 합니다. 리뷰어가 알림을 받고 PR 을 열었을 때 자기 리뷰가 이미 올라와 있어야 하기 때문입니다.

## 여러 PR 로 나눈 작업

계획이 작업을 여러 PR 로 나누었으면 PR 을 하나씩 처리합니다. 한 PR 의 구현, 1~7단계, 게시 승인이 끝난 뒤에 다음 PR 의 구현을 시작합니다. 앞 PR 의 리뷰 결과가 뒤 PR 에 반영되게 하기 위해서입니다.

- **브랜치**: PR 마다 작업 브랜치를 따로 둡니다. 앞 PR 에 의존하는 PR 은 앞 PR 의 브랜치에서 갈라져 나오고, 드래프트의 base 도 앞 PR 의 브랜치로 둡니다. 의존하지 않는 PR 은 프로젝트의 기본 base 에서 갈라집니다.
- **리뷰 범위**: 리뷰 서브에이전트에 그 PR 의 base 를 알려서, 앞 PR 의 변경이 아니라 그 PR 의 변경만 보게 합니다. PR 마다, 그리고 재리뷰마다 새 서브에이전트를 씁니다.
- **앞 PR 이 바뀌었을 때**: 팀 리뷰나 재수정으로 앞 PR 의 HEAD 가 바뀌면, 뒤 PR 을 그 위로 다시 맞추고(rebase) 검사를 다시 돌립니다. 맞추면서 뒤 PR 의 변경 내용이 달라졌으면 바뀐 부분을 재리뷰합니다.
- **앞 PR 이 머지되었을 때**: 뒤 PR 의 base 를 프로젝트의 기본 base 로 바꿉니다(`gh pr edit --base`). 머지는 사용자나 팀이 합니다. 이 스킬은 머지하지 않습니다.
- **6단계에서 함께 보여 줄 것**: 전체 PR 목록에서 지금이 몇 번째인지, 이 PR 의 base, 남은 PR.
- **PR 목록을 바꿔야 할 때**: 구현 중에 PR 을 더 나누거나 합쳐야 하면 멈추고 계획을 고쳐서 다시 승인받습니다.

## 흔한 착각

| 드는 생각 | 실제 |
|---|---|
| 「드래프트니까 리뷰어를 미리 지정해도 된다」 | 드래프트여도 지정하면 알림이 갑니다. 승인 뒤에 지정합니다. |
| 「본문은 간단히 직접 쓰자」 | 프로젝트의 PR 스킬이 정한 분석과 형식을 따릅니다. 바꾸는 것은 2단계 표의 세 가지뿐입니다. |
| 「고친 결함도 기록으로 코멘트에 남기자」 | 팀원이 이미 없는 문제를 읽게 됩니다. 요약 한 단락이면 충분합니다. |
| 「리뷰가 깨끗하니 바로 Ready 로 바꾸자」 | 자기 리뷰는 독립성이 낮습니다. 전환은 사용자가 결정합니다. |
| 「결정 필요 항목도 합리적인 쪽으로 고쳐 두자」 | 버려진 쪽의 불변식을 사용자가 모르게 됩니다. 올립니다. |
| 「마이너도 전부 고쳐서 깨끗하게 올리자」 | 반복이 길어지고 diff 가 커집니다. 한 곳에서 끝나는 것만 고치고 나머지는 남깁니다. |
| 「재리뷰에서 나온 것 하나만 더 고치면 끝난다」 | 두 번째 수정은 하지 않습니다. 수정한 자리에서 다시 나온 결함은 구조 원인입니다. 멈추고 보여 줍니다. |
| 「뒤 PR 도 미리 만들어 두면 빠르다」 | 앞 PR 의 리뷰에서 구조가 바뀌면 뒤 PR 을 전부 다시 맞춰야 합니다. 앞 PR 의 승인 뒤에 시작합니다. |
| 「재리뷰는 맥락을 아는 첫 리뷰 서브에이전트에 시키자」 | 그 서브에이전트는 턴마다 가득 찬 컨텍스트를 다시 읽습니다. 새 서브에이전트에 항목 파일과 수정 diff 만 넘깁니다. |
| 「작은 PR 이지만 적대 검토자도 띄우자」 | 조건(400줄 이상, 또는 크리티컬·메이저 후보)에 해당할 때만 1명 띄웁니다. |
| 「서브에이전트가 낸 항목을 전부 다시 재현하자」 | 고칠 항목만 고치기 직전에 재현합니다. |
| 「검사 하나가 원래 실패하던 것이니 넘어가자」 | 부모 커밋에서도 실패하는지 확인한 뒤에만 기존 실패로 적습니다. |
