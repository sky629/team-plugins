# make_spec

구현하기 전에 사용자가 **무엇을, 왜** 원하는지 확인하고, 그 내용을 스펙 문서로 써서 승인받는 스킬입니다. 스펙 승인에서 끝납니다. 구현은 하지 않습니다.

## 목적과 배경

요청을 읽고 떠올린 「사용자가 원하는 것」은 대개 실제보다 얕습니다. 사용자도 원하는 것을 끝까지 정리하지 못한 경우가 많습니다. 이유를 알면, 사용자가 말하지 않은 많은 결정을 사용자가 했을 방식으로 내릴 수 있습니다.

pstack 은 코드 구조를 정하고 검증하는 일을 잘하지만, 사람에게 묻지 않도록 설계되어 있습니다. 그래서 정책, UX, 범위처럼 사용자만 답할 수 있는 결정은 이 스킬이 먼저 확인합니다. 역할을 다음과 같이 나눕니다.

| 정하는 것 | 담당 |
|---|---|
| 무엇을 만드는가, 왜 만드는가, 무엇을 만들지 않는가 | 이 스킬 |
| 사용자가 직접 정하고 싶어 하는 구현 방법 | 이 스킬 |
| 타입, 함수 시그니처, 모듈 경계, 파일 배치 | pstack `architect` |
| 구현과 검증 | pstack `/poteto-mode` |

## 1. 묻기 전에 읽는다

첫 메시지를 쓰기 전에 다음을 읽습니다.

- 사용자가 가리킨 파일, 이슈, 기존 스펙, 이전 대화
- 그것과 연결된 코드. 관련 부분이 현재 어떻게 동작하는지, 이 변경이 무엇을 건드리는지 설명할 수 있을 때까지 읽습니다.
- 프로젝트의 규칙 문서(CLAUDE.md)와 용어표가 있으면 그 문서

프로젝트나 주어진 자료가 이미 답하는 것은 묻지 않습니다. 사용자가 이미 결정한 것을 다시 열지 않습니다.

## 2. 첫 메시지

약 200단어 안에서 다음을 순서대로 씁니다.

1. 요청을 자기 말로 다시 적습니다: 무엇을 원하는가, 누구를 위한 것인가, 왜 원하는가(사용자가 말한 범위까지만).
2. 읽어서 확인한 사실을 적습니다: 관련 부분의 현재 동작과 이 변경이 건드리는 곳.
3. 사용자가 고려하지 않았을 수 있고 요청 내용이나 구현 방식을 바꿀 사실(제약, 충돌, 더 저렴한 경로)이 있으면 분명하게 적습니다.
4. 틀린 부분을 고쳐 달라는 한 줄을 적습니다.
5. 질문 하나로 끝냅니다.
   - 이유를 아직 듣지 못했으면, 짐작할 수 있더라도 이유를 묻습니다. 사용자의 표현을 쓴 열린 질문으로 묻고, 선택지를 붙이지 않습니다.
   - 이유를 이미 알고 있으면, 답에 따라 만드는 것이 가장 크게 달라지는 결정 하나를 묻습니다.
   - 열린 결정이 없고 합리적인 방법이 하나뿐이면, 짧은 설계(접근, 다른 방법이 맞지 않는 이유, 설계 몇 줄)를 적고 승인을 요청합니다.

구현 방법은 이 메시지에서 다루지 않습니다. 진행 절차를 설명하지 않고 바로 질문합니다.

## 3. 대화

**질문하는 조건.** 답에 따라 만드는 것이 달라지고, 요청과 프로젝트 어느 쪽도 답하지 않을 때만 묻습니다. 그 밖의 결정은 직접 내리고, 이유와 함께 「제안」으로 말해 사용자가 고칠 수 있게 합니다. 문서 위치, 추가 조사, 보여 주는 방식 같은 절차상의 결정은 묻지 않고 실행한 뒤 알립니다.

**한 번에 하나씩 묻습니다.** 사용자가 쓰는 어휘를 그대로 쓰고, 절차 용어를 쓰지 않습니다.

**이유를 알기 전에는 열린 질문을 합니다.** 예시 답을 붙이지 않습니다. 선택지는 사용자의 답을 그쪽으로 유도하고, 사용자 자신의 표현에는 선택지에 없는 의도가 들어 있습니다.

**이유를 안 뒤에는 선택지를 구체적으로 보여 줍니다.** 선택지를 이름 붙일 수 있는 결정이면 `AskUserQuestion` 으로 묻습니다. 선택지마다 잃는 것을 적고, 권장안을 첫 번째에 둡니다. 사용자가 「알아서 해」 또는 「어떻게 생각해?」 라고 하면 구체적인 안을 제안합니다.

**질문은 이 프로젝트에 고유해야 합니다.** 사용자의 직전 답이나 코드에서 찾은 사실 위에 다음 질문을 세워서, 사용자가 놓친 결과나 경우를 생각해 보게 합니다. 예: 「투표는 회의 전에 마감되는데 이번 달에 두 명이 새로 들어왔습니다. 회차 중간에 들어온 사람도 투표할 수 있습니까?」 이유가 분명하지 않으면 답이 무엇을 바꾸는지 함께 말합니다.

**관찰로 알 수 있는 것은 묻지 않고 확인합니다.** 동작, 출력, 성능, 기존 구현의 유무는 코드를 읽거나 실행해서 확인하고, 무엇을 찾았는지 말합니다.

**확인할 영역.** 아래는 다뤄야 할 영역입니다. 목록을 그대로 질문으로 읽지 않습니다.

- 이것이 어떤 종류의 기능이고 무엇이 특별한가
- 왜 지금 필요한가, 사용자가 보는 성공은 무엇인가
- 목표, 하지 않는 것, 반목표(기술적으로는 동작해도 실패로 볼 결과)
- 다른 곳에서 본 사례 중 좋았던 것과 싫었던 것
- 현재 상태: 지금 있는 것, 이미 시도한 것
- 사용자가 신경 쓰는 세부 사항

**구현 방법을 누가 정하는가.** 사용자가 구현 방법을 먼저 꺼내거나 트레이드오프를 물으면, 선택지와 권장안을 보여 주고 사용자가 고르게 합니다. 사용자가 결과만 말하면 구현 방법은 넘겨받은 것입니다. 기존 코드가 이미 쓰는 것을 따릅니다. 사용자가 정하지 않은 선택은 스펙에 「사용자가 동의한 것」으로 적지 않습니다.

**말보다 보여 줍니다.** 화면, 배치, 흐름처럼 눈으로 보는 것은 텍스트 스케치를 설명 옆에 둡니다. 모양 자체가 사용자의 결정이면 HTML 목업을 제안합니다.

**직접 해 봐야 알 수 있으면 시험 구현을 제안합니다.** 사용자가 승인하면 pstack 의 Prototype 플레이북으로 버릴 코드를 만들고, 배운 것을 대화로 가져옵니다. 시험 구현을 유지하는 것은 새 요청이므로 승인 절차를 다시 거칩니다.

## 4. 이해한 부분을 되돌려 말한다

한 부분(무엇을 위한 것이고 누구를 위한 것인지, 또는 한 부분의 동작)을 설명할 수 있을 만큼 이해하면, 그 부분을 200~300단어로 되돌려 말한 뒤 다음 부분의 질문으로 돌아갑니다. 되돌려 말하기와 질문을 대화가 끝날 때까지 번갈아 합니다.

- 사용자가 말한 것만 「사용자의 것」으로 적습니다.
- 직접 채운 것은 이유와 함께 「제안」으로 적습니다.
- 각 부분의 끝에서 틀린 것과 빠진 것을 묻습니다.

## 5. 접근 방식을 제시한다

원하는 것을 이해한 뒤, 스펙을 쓰기 전에, 접근 방식을 별도의 메시지로 제시합니다.

1. 실제로 다른 대안을 여러 개 만듭니다.
2. 약한 대안을 뺍니다. 사용자의 이유에 어긋나는 것과 기존 코드가 배제하는 것이 여기에 들어갑니다.
3. 남은 두세 개를 떠올릴 수 있을 만큼 구체적으로 적습니다. 프로젝트의 실제 구조에 근거를 두고, 대안마다 잃는 것을 적습니다.
4. 하나를 권하고 이유를 말한 뒤, 사용자가 고르게 합니다.

접근 방식은 **동작과 책임의 수준**에서 적습니다. 예: 「서버가 파일을 만든다」 대 「브라우저가 파일을 만든다」, 「기존 화면에 넣는다」 대 「새 화면을 만든다」. 타입, 시그니처, 모듈 경계, 파일 배치는 적지 않습니다. 그 부분은 `architect` 가 여러 모델의 경합으로 정합니다.

합리적인 방법이 하나뿐이면 그렇다고 말하고, 다른 방법이 맞지 않는 이유를 적습니다.

## 6. 작업 크기를 말한다

접근 방식이 정해지면 작업 크기를 말합니다. 사용자가 바꿀 수 있습니다.

| 크기 | 스펙 |
|---|---|
| 작은 변경 | 짧은 스펙: 대화에서 다룬 내용을 항목마다 한두 줄로 적습니다. 구현자 점검은 하지 않습니다. |
| 프로젝트 | 전체 스펙(아래 형식)을 쓰고 구현자 점검을 합니다. |

도중에 작업이 커지면 멈추고 알린 뒤 크기를 올립니다. 독립된 프로젝트 여러 개로 보이면 그렇다고 말하고, 순서에 합의한 뒤 하나씩 진행합니다.

## 7. 스펙을 쓴다

**위치.** 사용자의 규칙(CLAUDE.md, 메모리)이 스펙을 두는 경로를 정했으면 그 경로 아래 `specs/YYYY-MM-DD-<topic>-design.md` 에 씁니다. 정한 경로가 없으면 어디에 둘지 한 번 묻습니다. 사용자의 규칙이 레포 안을 지정하지 않았으면 레포 안에 쓰지 않고 커밋하지 않습니다. 같은 폴더에 기존 스펙이 있으면 그 머리말 형식과 절 번호 관례를 따릅니다.

**기준.** 사용자에게 다시 물을 수 없는 구현자가 이 문서만 읽고 계획을 세울 수 있어야 합니다.

**형식.**

```markdown
# <기능 이름> 설계

- 작성일: YYYY-MM-DD
- 기준 코드: <브랜치> `<커밋>`
- 상태: 승인 대기

## 1. 목적
무엇을 만드는가, 누구를 위한 것인가, 왜 지금 필요한가.

## 2. 사용 시나리오
누가 무엇을 하고 어떤 결과를 얻는가. 화면이나 흐름은 텍스트 스케치를 붙인다.

## 3. 완료 조건
반증할 수 있는 문장으로 적는다. 조건마다 확인 방법(명령, 화면에서 볼 결과)을 붙인다.

## 4. 목표, 하지 않는 것, 반목표
반목표는 기술적으로 동작해도 실패로 보는 결과다.

## 5. 제약
기존 계약, 규칙, 성능, 배포 순서 등.

## 6. 접근 방식
검토한 두세 가지, 각각 잃는 것, 고른 것과 이유.

## 7. 결정한 것
| 결정 | 정한 사람(사용자 / 제안) | 이유 |

## 8. 확인한 사실
현재 동작과 근거(`파일:줄`).

## 9. 구현자에게 맡기는 것
타입, 모듈 경계, 파일 배치 등 `architect` 가 정할 구조 관련 질문.

## 10. 위험과 되돌리기 어려운 지점
```

- 「정한 사람」 열에서 사용자가 말한 결정과 직접 채운 제안을 구분합니다.
- 사용자가 답하지 않은 제품 결정은 추측으로 채우지 않고 「미결」 로 적습니다. 미결이 남아 있으면 승인을 요청하지 않습니다.
- 프로젝트에 용어표가 있으면 새 용어를 그 표의 규칙에 맞춥니다.

## 8. 구현자 점검 (프로젝트 크기만)

스펙을 쓴다고 알릴 때, 검토자가 먼저 읽고 질문이 한 번 돌아올 수 있다고 말합니다.

1. 이 디렉터리의 `builder-check-prompt.md` 로 새 서브에이전트를 실행합니다. 대화 내용을 넘기지 않고 스펙 경로만 넘깁니다.
2. 돌아온 질문을 셋으로 나눕니다.
   - **이미 답이 있는 것**(대화나 프로젝트가 답함): 답을 스펙에 넣습니다.
   - **사소한 것**(합리적인 구현자가 정해도 만드는 것이 달라지지 않음): 직접 정하고 스펙에 「제안」으로 표시합니다.
   - **사용자의 것**(사용자만 답할 수 있고 답에 따라 만드는 것이 달라짐): 사용자에게 가져갑니다.
3. 「사용자의 것」을 중요한 순서로 한 메시지에 모아 묻습니다.
4. 답을 스펙에 반영합니다.

점검으로 생기는 질문은 이 한 번뿐입니다. 점검이 끝나기 전에는 스펙을 넘기지 않습니다.

## 9. 승인을 받는다

다음을 보여 주고 멈춥니다.

- 스펙 파일의 절대 경로
- 세 줄 이내의 요약
- 직접 내린 결정(「제안」)의 짧은 목록. 사용자가 읽으면서 확인할 항목입니다.

수정 요청이 오면 스펙을 고치고 다시 승인을 요청합니다. 「좋아 보여」 는 그때까지 보여 준 것에 대한 승인입니다. 아직 쓰지 않은 스펙은 승인된 것이 아닙니다.

**스펙이 승인되기 전에는 아무것도 만들지 않습니다.** 제품 코드 작성, 스캐폴딩, 의존성 설치, 구현 스킬 호출이 모두 여기에 들어갑니다. 읽기와 조사는 해도 됩니다. 예외는 사용자가 승인한 시험 구현 하나입니다.

## 10. 인계

승인되면 스펙의 「상태」를 `승인됨 (YYYY-MM-DD)` 으로 바꾸고, 사용자가 붙여 넣을 한 줄을 출력합니다.

```
/poteto-mode <스펙 절대 경로> 를 구현한다.
- 7절의 결정은 확정이므로 바꾸지 않는다. 증거가 결정과 어긋나면 구현을 멈추고 보고한다.
- 9절은 architect with checkpoint 로 정한다.
- 구현 전에 구현 계획을 <플랜 절대 경로> 에 쓴다. 단계마다 건드리는 파일, 그 단계의 산출물, 확인 방법을 적는다. 합성한 설계와 이 계획을 함께 보여 주고 승인을 받은 뒤 구현한다.
- 3절의 완료 조건으로 검증한다.
- 끝나면 7절의 결정마다 지켰는지와 근거(파일:줄 또는 실행 결과)를 표로 보고한다. 지키지 못한 결정은 이유를 적는다.
- 그 뒤 <run_final_check 스킬 파일의 절대 경로> 를 읽고 따른다. 그 파일이 정한 것 외의 PR 생성·게시는 하지 않는다.
```

꺾쇠로 적은 경로 세 개는 실제 절대 경로로 채워서 출력합니다.

- 스펙 경로: 7단계에서 쓴 파일입니다.
- 플랜 경로: 스펙 폴더와 같은 상위 폴더의 `plans/YYYY-MM-DD-<topic>.md` 입니다. 스펙과 같은 날짜와 주제 이름을 씁니다.
- `run_final_check` 스킬 파일: 이 스킬 폴더와 같은 상위 폴더에 있는 `run_final_check/SKILL.md` 입니다. 파일이 있는지 확인한 뒤에 적습니다. 없으면 그 줄을 「푸시와 PR 은 하지 않는다」 로 바꾸고 사용자에게 알립니다. 작업이 여러 PR 로 나뉘면 다음 줄을 더합니다.

```
- 여러 PR 로 나눈다. Multi-phase plan 플레이북으로 계획을 쓰고, 계획의 PR 목록(순서, 각 PR 의 범위, 의존 관계)을 설계와 함께 승인받는다. Autopilot 플레이북은 쓰지 않는다. 계획의 PR 을 하나씩 구현하고, PR 마다 run_final_check 를 따른다. 앞 PR 의 게시 승인을 받은 뒤에 다음 PR 을 시작한다.
```

pstack 의 Autopilot 플레이북은 PR 을 Ready 상태로 열고 병렬로 만들며, Autopilot-full 은 머지까지 합니다. 이 줄이 그 동작을 막습니다.

각 줄을 넣는 이유는 다음과 같습니다. 작은 변경이 아니면 빼지 않습니다.

- `with checkpoint`: `architect` 는 기본값으로 사용자 확인 없이 구현으로 넘어갑니다. 이 문구가 있어야 구조 설계를 구현 전에 볼 수 있습니다.
- 구현 계획: pstack 은 기본값으로 구현 순서를 문서로 남기지 않습니다. 계획이 있어야 사용자가 순서와 범위를 구현 전에 고칠 수 있습니다.
- 결정 준수 표: pstack 은 완료 조건으로 검증하고, 스펙의 결정을 지켰는지는 따로 대조하지 않습니다.
- `run_final_check`: 드래프트 PR 생성(프로젝트의 PR 스킬), 자기 리뷰, 수정, 게시 승인, Ready for review 전환까지의 절차는 `run_final_check` 스킬에 있습니다. 이 스킬은 그 파일을 가리키기만 합니다. pstack 의 플레이북은 기본값으로 PR 을 바로 만들기 때문에 이 줄로 범위를 제한합니다. PR 없이 끝내려면 이 줄을 「푸시와 PR 은 하지 않는다」 로 바꿉니다.

`/poteto-mode` 를 직접 호출하지 않습니다. 구현은 사용자가 시작합니다.

## 흔한 착각

| 드는 생각 | 실제 |
|---|---|
| 「사용자가 원할 만한 것을 메뉴로 보여 주자」 | 선택지는 답을 유도합니다. 먼저 사용자가 직접 설명하게 합니다. |
| 「합리적인 기본값으로 채우자」 | 괜찮습니다. 다만 소리 내어 말합니다. 듣지 못한 기본값은 거절할 수도 없습니다. |
| 「질문에 답을 받았으니 스펙을 쓰자」 | 접근 방식을 먼저 별도의 메시지로 제시합니다. |
| 「절차를 먼저 설명하자」 | 바로 질문합니다. 절차는 진행하면서 드러납니다. |
| 「아이디어에 '좋네요' 라고 했다」 | 승인은 보여 준 것에만 해당합니다. |
| 「구조도 스펙에 정해 두면 구현이 빠르다」 | 구조는 `architect` 가 경합으로 정합니다. 스펙이 구조를 정하면 그 경합이 의미를 잃습니다. |
| 「코드를 보면 알 수 있지만 물어보는 편이 빠르다」 | 관찰로 알 수 있는 것은 사용자가 답할 일이 아닙니다. 직접 확인합니다. |
| 「시험 구현이 동작하니 그 위에 계속 만들자」 | 유지하는 것은 새 요청입니다. 승인 절차를 다시 거칩니다. |

## 출처

대화 절차(읽고 나서 묻기, 열린 질문, 되돌려 말하기, 접근 방식 제시, 구현자 점검, 승인 전 구현 금지)는 [obra/superpowers](https://github.com/obra/superpowers)(MIT)의 `brainstorming` 스킬을 pstack 과 함께 쓰도록 고쳐 옮긴 것입니다. 재진술과 완료 조건 항목은 pstack 의 `in-your-own-words`, `sharpen`, `figure-it-out` 에서 가져왔습니다.
